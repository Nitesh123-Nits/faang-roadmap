Domain-Driven Design (DDD) Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Structuring software around a model of the business domain using a ubiquitous language, bounded contexts and tactical building blocks.

Strategic design splits the domain into bounded contexts; tactical design models rules with aggregates, entities, value objects and domain events.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

The gap between business understanding and code, and unclear service or module boundaries.

Eric Evans (2003) addressed complex domains where technical models diverged from the business.

Bounded contexts with a context map; aggregates inside each

How it works

Domain experts and engineers build a ubiquitous language.
The domain is split into bounded contexts with explicit boundaries.
A context map defines relationships (customer–supplier, ACL, shared kernel).
Inside a context, aggregates enforce invariants through one root.
Domain events publish meaningful state changes to other contexts.
An anti-corruption layer translates between models where needed.
