II.07

Modular Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Decomposing software into cohesive modules with defined interfaces, hidden internals and explicit dependencies, independent of how they are deployed.

Modularity is about boundaries and interfaces; deployment (one binary or many) is a separate decision.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Systems where any code can call any other code, causing ripple effects and no ownership.

Information hiding (Parnas, 1972) remains the base principle behind libraries, plug-ins and services.

How it works

Identify cohesive capabilities and define module boundaries.
Expose a small, stable public interface per module.
Hide internals using visibility rules (JPMS, packages).
Declare explicit module dependencies, avoiding cycles.
Verify dependencies automatically in the build.
Evolve modules independently within contract stability.

When not to use
