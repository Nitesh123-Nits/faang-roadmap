Database-per-Service Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Each microservice owns its private database, and other services access that data only through the owning service’s API or events.

Data ownership defines service autonomy: no shared tables, no cross-service joins.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Hidden coupling through shared schemas that block independent deployment and evolution.

A shared database turns microservices into a distributed monolith; private data enables independent change.

Each service has its own datastore; sharing happens through APIs and events

How it works

Each service chooses the datastore that fits its workload.
Only the owning service reads and writes its data.
Other services request data through the owner’s API.
State changes are published as events.
Consumers keep their own local copies (read models) if needed.
Cross-service consistency is handled through sagas.

When not to use
