III.15

Batch Processing Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Process large volumes of data in scheduled, bounded jobs rather than continuously.

Collect data over a window, then process it as a whole for throughput and efficiency.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Heavy computation over large datasets where latency is not critical.

The original mainframe processing model; still the most cost-effective for large-scale transformations and reporting.

Scheduled jobs read, process and write in chunks
Infrastructure
Database / store
Service / component

Sync call

How it works

A scheduler triggers the job at a set time.
The job reads input in chunks.
Each chunk is processed and validated.
Results are written with commit checkpoints.
Failures restart from the last checkpoint.
The job reports status and metrics on completion.
BATCH PROCESSING ARCHITECTURE

Advantages

High throughput and efficient resource use.

+ Simple, deterministic and re-runnable.

Cheap compute (off-peak).
Easy to audit and test with fixed inputs.

When to use

Nightly settlements, billing, reporting, ETL and data migration.

Real-world applications

End-of-day bank settlements
Payroll runs
Data warehouse loads
Spring Batch jobs.

Quick summary

PRIMARY PURPOSEScheduled bulk processing
SCALABILITYHigh
COUPLINGLow
MAIN DRAWBACKHigh latency / stale data

Disadvantages

High latency; data is stale between runs.
Failures late in a run are expensive.
Peaks in resource usage and batch windows.
Not suitable for real-time needs.

When not to use

Real-time or interactive needs; use stream processing instead.

Key engineering considerations

Make jobs idempotent and restartable. Use chunking and checkpoints. Monitor SLAs for batch windows. See Lambda vs Kappa (Part IX).
