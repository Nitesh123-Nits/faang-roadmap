Notification Platform

A shared internal platform that delivers email, SMS, push and in-app messages reliably at scale. It illustrates queue-based load leveling, per-channel isolation and idempotent delivery.

MAJOR SERVICES & COMPONENTS
COMMUNICATION MECHANISMS

Notification API, Template service, User preference service, Router and rate limiter, Channel workers, Delivery tracker, Provider adapters.

Producers send requests via API or Kafka; per-channel queues decouple speeds; workers call provider APIs; delivery receipts return via webhooks.

DATA STORAGE ARCHITECTURE
EXTERNAL DEPENDENCIES

Request log in Kafka; status and deduplication store (Redis/DynamoDB); template store; preference database; analytics store.

Email (SES/SendGrid), SMS gateways, APNs/FCM, WhatsApp APIs.

CHOSEN ARCHITECTURAL STYLE
WHY THIS ARCHITECTURE WAS SELECTED

Message-driven architecture with competing consumers, ports-and-adapters provider integrations and per-channel bulkheads.

Providers are slow, rate-limited and flaky, so queues absorb bursts and isolate channels. Adapters make providers replaceable; idempotency keys prevent duplicate sends.

KEY TRADE-OFFS

At-least-once delivery requires dedupe; ordering is weak; provider failover logic; compliance with user preferences and quiet hours adds complexity.
