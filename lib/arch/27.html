Backend-for-Frontend (BFF) Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A dedicated backend per client experience (web, mobile, partner) that aggregates and shapes downstream service data.

Give each frontend its own tailor-made API layer so general-purpose services do not accumulate clientspecific logic.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

One-size-fits-all APIs that cause over-fetching, chatty calls and conflicting client requirements.

Mobile and web clients diverged in needs; Sam Newman and SoundCloud popularized per-client backends.

One BFF per client type in front of shared domain services

How it works

A client calls its own BFF.
The BFF authenticates, then fans out to the domain services it needs.
It aggregates, filters and reshapes responses for that client.
It handles client-specific concerns: pagination, payload size, protocol.
Domain services stay generic and stable.
Each BFF is owned and released by the client team.
BACKEND-FOR-FRONTEND (BFF) ARCHITECTURE

Advantages

Disadvantages

Optimized payloads and fewer round trips per client.

+ Client teams move independently.

More services to run and duplicate logic across BFFs.

+ Keeps client logic out of core services.

Risk of logic drift between BFFs.

+ Different protocols (GraphQL, REST) per client.

Another hop adds latency.
Needs clear ownership.

When to use

When not to use

Multiple client types with different data and interaction needs on a shared service backend.

A single client, or when a gateway with simple routing is sufficient.
