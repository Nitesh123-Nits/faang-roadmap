Distributed Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A system whose components run on multiple networked machines and coordinate by exchanging messages to appear as one system.

Spread computation and data across nodes to gain scale, availability and locality, and accept partial failure as normal.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Limits of a single machine in capacity, throughput, availability and geographic reach.

Data growth and availability demands exceeded vertical scaling; commodity clusters became the economical answer.

Cluster with partitioned and replicated data, coordinated across nodes

How it works

Requests are spread across nodes by a load balancer.
Data is partitioned (sharded) so each node owns a subset.
Each partition is replicated for availability.
Nodes coordinate through consensus or a coordination service.
Failures are detected via heartbeats and traffic is rerouted.
The system trades consistency, latency and availability per CAP/PACELC choices.
DISTRIBUTED ARCHITECTURE

Advantages

Horizontal scalability and high availability.

+ Geographic distribution reduces latency.

Fault tolerance through replication.
Cost-efficient on commodity hardware.

When to use

Systems exceeding a single node’s capacity or needing high availability and geographic reach.

Real-world applications

Search engines
Distributed databases (Cassandra, Spanner)
Large messaging platforms
Global e-commerce.

Quick summary

Disadvantages

Partial failures, network partitions and clock skew.
Consistency is hard; debugging is hard.
Operational and cognitive overhead.
Cost of coordination and data movement.

When not to use

Workloads that comfortably fit on one reliable node; prefer a simpler design and replication for backup.

Key engineering considerations

Design for idempotency, retries with backoff, timeouts and circuit breakers. Choose consistency model explicitly. Plan partition tolerance, observability and chaos testing.
