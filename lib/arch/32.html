Request–Response Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A requester sends a message and waits for a correlated response from the receiver.

The simplest interaction model: a synchronous exchange where the caller needs the result to continue.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Giving callers immediate results with straightforward semantics and error handling.

It maps naturally to function calls and underlies HTTP, RPC and database access.

How it works

The client sends a request and starts a timeout.
The service validates and authorizes it.
It performs work, possibly calling dependencies synchronously.
It returns a response with data or an error status.
The client handles success, error or timeout.
Retries must be idempotent and use backoff.
