II.09

Plugin-Based Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A host application with a stable extension API into which third-party or optional plug-ins are loaded at runtime.

Keep a small stable host and push variable features into independently developed plug-ins that conform to a contract.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Letting others extend an application without changing or recompiling its core.

Ecosystems (IDEs, browsers, CMSs) need extensibility and isolation of optional features.

Host application discovers and loads plug-ins through an extension API

How it works

The host exposes extension points and a plug-in contract.
A registry discovers plug-ins (classpath, ServiceLoader, directory).
Plug-ins are validated and loaded, optionally in isolated class loaders.
The host calls plug-ins through the contract.
Plug-ins may register UI, commands or handlers.
Plug-ins are enabled, upgraded or removed without changing the core.
PLUGIN-BASED ARCHITECTURE

Advantages

Disadvantages

Extensibility without core changes.
API stability and versioning obligations.

+ Third-party ecosystem and optional features.

Security and sandboxing concerns.
Isolation of faulty extensions.
Plug-in interactions are hard to test.
Smaller core with faster stabilization.
Dependency conflicts between plug-ins.

When to use

When not to use

Platforms with an ecosystem: IDEs, build tools, CMSs, payment connectors, rule providers.

Closed applications with no external extension need.
