Shared Database Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Multiple services or applications read and write the same database schema.

A common data store is the integration mechanism, giving simple joins and transactions across components.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

The complexity of data synchronization and distributed transactions during early decomposition.

Legacy integration and simple systems often start here; it is easy and consistent.

How it works

Services connect directly to the shared database.
Each reads and writes tables as needed.
ACID transactions span tables from multiple components.
A schema change affects every service using it.
Deployments must be coordinated around schema versions.
Performance contention and locks affect all consumers.

Advantages

Disadvantages

Simple integration and joins.

+ Strong consistency via local ACID transactions.

Tight coupling through the schema; coordinated releases.

+ Easy reporting and querying.

Contention and a single scaling bottleneck.

+ Quick to implement.

Unclear ownership of data and rules.
Blocks independent technology choices.

When to use

When not to use

Small systems, a transitional step in migrations, or tightly related legacy applications.

Independent teams and services needing autonomy and independent deployment.
