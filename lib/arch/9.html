Modular Monolith Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A single deployable application whose internals are split into strongly encapsulated modules with explicit public APIs.

Get microservice-style boundaries and team ownership without paying the network and operations cost.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

The big ball of mud in monoliths, and premature distribution.

Teams that over-adopted microservices rediscovered that boundaries, not network hops, deliver most of the benefit.

One deployable, modules communicate only via public interfaces

How it works

Requests enter one application host.
The host delegates to a module through its public API.
Modules never access each other’s internals or tables.
Cross-module reactions use in-process domain events.
Each module owns its schema within the shared database.
A module can later be extracted to a service along its existing boundary.

Advantages

Disadvantages

Strong boundaries with simple deployment and local transactions.
Boundaries depend on discipline and tooling to stay enforced.
Lower infra and operations cost than microservices.
Single scaling and deployment unit remains.
Refactoring across modules stays cheap.

+ Natural path to service extraction.

A shared database can still tempt cross-module coupling.
One bad module can affect process stability.

When to use

When not to use

Mid-sized products, growing teams, and domains where service boundaries are still being discovered.

Hard requirements for independent scaling, polyglot runtimes or fully independent release cadences.

Real-world applications

Key engineering considerations

SaaS back offices

Enforce rules with Java modules, ArchUnit or Spring Modulith. Give each module its own schema and forbid cross-schema joins. Use domain events for crossmodule reactions.
