Selecting an architecture

There is no universally best architecture. Every architecture in this handbook optimizes some quality attributes by sacrificing others. Selection is a structured exercise: translate business needs into measurable quality attributes, filter by constraints, compare candidates through explicit trade-offs, and record the decision.

Rule of thumb: choose the simplest architecture that satisfies today’s measurable requirements and keeps tomorrow’s likely changes cheap. Complexity should be purchased only against a named, current need.

Trade-off evaluation: four questions before committing

What does this make harder? Name the quality attribute you are sacrificing and whether the business accepts it.
What is the reversibility? Prefer decisions that are cheap to undo (modules, feature flags) over those that are not (data ownership splits, public contracts).
Who pays the operational cost? Count on-call load, tooling, skills and infrastructure, not just design elegance.
What evidence would change the decision? Write the revisit triggers into the ADR (traffic, team count, SLO breach).

Architecture Decision Record (example)

An ADR captures one significant decision with its context, options and consequences, so future engineers understand why, not just what. Keep them short, immutable once accepted, and supersede rather than edit.

ADR-014: Use a modular monolith with Kafka-based integration for the Order Platform
Status:    Accepted                       Date: 2026-11-03
Deciders:  Platform architect, Order team lead, SRE lead
Context:   One team of 8 engineers; domain boundaries (Orders, Payments, Catalog) still
           evolving; peak 300 orders/s; SLO 99.9%; two engineers on call; need to integrate
           with a legacy ERP and a payment gateway. Time-to-market target: 4 months.
Decision:  Build one deployable with three modules, each owning a schema and exposing a
           public API. Publish domain events to Kafka through a transactional outbox for the
           ERP and analytics consumers. Defer microservices.
Options:   1. Microservices from day one   - rejected: ops load and boundary uncertainty
           2. Layered monolith              - rejected: boundary erosion, hard to split later
           3. Modular monolith + outbox     - chosen
Consequences:
  (+) Local ACID transactions; one pipeline; fast delivery; clean path to extraction.
  (+) ERP/analytics decoupled via events without distributed transactions.
  (-) Single scale and release unit; module boundaries need ArchUnit enforcement.
  (-) Kafka and the outbox relay add operational surface.
Revisit when: team > 3 squads, or any module needs independent scaling or a distinct SLO,
           or release contention exceeds 2 blocked merges/week. Review date: 2027-05-01.

ADR practice

Store ADRs in the repository next to the code (docs/adr/NNN-title.md) and review them like code.
One decision per record; link superseded records instead of rewriting history.
Include rejected options and the reason; this prevents re-litigating the same debate.
Add explicit revisit triggers and a review date so decisions do not become dogma.
