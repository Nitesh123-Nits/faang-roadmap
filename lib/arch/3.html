Monolithic Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

One deployable unit containing UI, business logic and data access, sharing a single process and usually a single database.

Keep everything in one codebase and one runtime so calls are in-process method calls and transactions are local ACID.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Distributed-system overhead (network calls, partial failure, versioning) for teams and products that do not need independent scaling.

It is the default shape of early enterprise software; microservices emerged later to relieve its scaling and team-coordination limits.

Single deployable — everything runs in one process

How it works

A request reaches the single application over HTTP.
The web layer routes to the relevant module in the same process.
Modules call each other through plain method calls.
Data changes happen inside one local database transaction.
The response returns; the whole artifact is built, tested and deployed together.
Scaling is done by running N identical copies behind a load balancer.

When to use

When not to use

Early-stage products, small teams, well-understood domains, internal tools, and any system whose scaling profile is uniform and moderate.

Many autonomous teams shipping independently, parts of the system with very different scaling or availability needs, or hard fault-isolation requirements.

Real-world applications

Key engineering considerations

Internal admin and back-office applications
early-stage SaaS MVPs
Line-of-business ERP modules
Content sites on a single framework.

Enforce internal module boundaries (packages, ArchUnit tests) to keep a later split possible. Run stateless instances behind a load balancer and scale the database vertically first. Keep a fast CI pipeline; use feature flags so deploy size does not equal release risk.
