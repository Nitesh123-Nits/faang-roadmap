Architecture terminology glossary

AggregateDDD cluster of entities and value objects treated as one consistency unit, accessed through a root.
Anti-corruptionTranslation layer that keeps an external or legacy model from leaking into your domain model.
layer
BackpressureMechanism by which consumers signal producers to slow down to avoid overload.
Bounded contextExplicit boundary within which a domain model and its language are consistent.
BulkheadIsolation of resources (pools, queues) so one failing part cannot exhaust the rest.
CAP theoremUnder a network partition a system must choose between consistency and availability.
CDCChange data capture: streaming database changes as events from the transaction log.
Circuit breakerStops calls to a failing dependency after repeated errors, then probes for recovery.
Consistent hashingKey-to-node mapping that moves minimal keys when nodes join or leave.
Control plane / dataConfiguration and policy management versus the traffic-carrying path.
plane
CRDTData type whose replicas merge deterministically without coordination.
Dead-letter queueQueue holding messages that could not be processed after retries.
DependencyHigh-level policy depends on abstractions; details implement them.
inversion
East–west / north–Service-to-service traffic inside a system versus client-to-system traffic.
south
Eventual consistencyReplicas converge to the same state if updates stop; reads may be stale meanwhile.
Exactly-onceEffects occur once, in practice via at-least-once delivery plus idempotent processing.
semantics
IdempotencyRepeating an operation yields the same result as performing it once.
Leader electionProcess by which cluster nodes agree on a single coordinator.
Noisy neighborA tenant or workload consuming shared resources at others’ expense.
Outbox patternWrite state and an event in one local transaction; relay the event afterwards.
PACELCExtends CAP: else (no partition) trade latency against consistency.
Partition / shardSubset of data owned by a node; sharding spreads data across nodes.
Port / adapterInterface owned by the core / implementation connecting it to a technology.
QuorumMinimum number of replicas that must agree for an operation to succeed.
Read model /Query-optimized view derived from events or write-side data.
projection
RPO / RTOMaximum tolerable data loss / time to restore service after a disaster.
SagaSequence of local transactions with compensations replacing a distributed transaction.
Service discoveryMechanism for finding live service instances at runtime.
Service levelTarget for a reliability metric, such as 99.9% availability.
objective (SLO)
SidecarHelper process deployed with an application instance sharing its lifecycle.
Split brainTwo parts of a cluster each believe they are the leader.
Stateless serviceService holding no per-client state between requests, enabling easy scaling.
Strangler figIncremental replacement of a legacy system behind a routing facade.
Two-phase commitAtomic commit protocol using prepare and commit phases across resources.
(2PC)
Ubiquitous languageShared vocabulary between domain experts and developers used in code.
Value objectImmutable object defined by its attributes rather than identity.
Vertical / horizontalAdding resources to a node versus adding nodes.
scaling
WatermarkStream-processing marker of event-time progress used to handle late data.
Write-behindCache writes data to the store asynchronously after acknowledging the write.
Zero trustNo implicit trust by network location; every request is authenticated and authorized.

Quick revision notes

Part I — Fundamental

Monolith: one deployable. Modular monolith: one deployable with enforced boundaries. Microservices: many deployables owning their data.
Distributed monolith is a diagnosis, not a design: distributed cost with monolithic coupling.
Layered is a code style; three-tier is a deployment topology.
EDA decouples via events; serverless removes server management; P2P removes the center.

Part II — Domain-centric

Clean, Hexagonal and Onion share one rule: dependencies point inward to the domain.
DDD gives boundaries (bounded contexts) and tactical patterns (aggregates, events).
Vertical slices optimize change per feature; screaming architecture reveals intent.
Microkernel: tiny core, everything else a module. Plug-in: complete host with extension points.
BFF: one backend per client experience; micro-frontends: independent UI deployables.

Part III — Styles and communication

Event = fact (past tense), command = request. Pub/sub fans out facts; queues distribute work.
CQRS splits read/write models; Event Sourcing stores history; they are independent.
Saga replaces distributed ACID with compensations; orchestrate complex flows, choreograph simple ones.
Batch for throughput, stream for latency; Lambda = two paths, Kappa = one path with replay.
Shared-nothing and space-based architectures exist to remove shared bottlenecks.

Part IV — Presentation

MVC → MVP → MVVM → MVI: progressively more explicit state flow.
Flux and Redux formalize unidirectional flow: action → reducer → store → view.
Components: props down, events up.

Part V — Microservices and distributed

Gateway = north–south; mesh = east–west; sidecar and ambassador are co-located helpers.
Database per service; share via APIs and events; compose reads with API composition or CQRS.
2PC blocks; sagas and outbox keep services available.
Multi-tenancy and cells trade cost against isolation and blast radius.
Active-active = all sites live; active-passive = one live, one standby.

Part VI — Data

Lake = cheap raw; warehouse = modeled and fast; lakehouse = ACID tables on lake storage.
Medallion layers: Bronze raw, Silver cleansed, Gold business-ready.
ETL transforms before load; ELT after load. Mesh is organizational, fabric is metadata-driven.
Cache hierarchy: browser → CDN → gateway → app → distributed → database.

Part VII — Cloud-native

Containers package; Kubernetes orchestrates; serverless abstracts servers.
HA removes single points of failure; fault tolerance contains failures; DR recovers from loss (RPO/RTO).
Multi-cloud costs a lot, multi-region on one cloud is usually enough; edge brings compute to the data.

Part VIII — Specialized

Rule-based: facts + rules + engine. Interpreter: parse then evaluate a DSL. Reflection: inspect and change behavior at runtime.
Primary–replica: one writer; leader–follower: consensus-elected leader.
Reactive: non-blocking with backpressure. Actor: private state + messages + supervision.
