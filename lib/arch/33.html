III.05

Event Sourcing

WHAT IS IT?
FUNDAMENTAL IDEA

Persist state as an append-only sequence of immutable events; current state is derived by replaying them.

The event log is the source of truth; state is a projection of history.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Lost history, hard audit trails and difficulty reconstructing how state came to be.

Domains like finance and ledgers need complete audit and temporal queries; also enables replay and new projections.

Commands append events; state and views are derived by replay

How it works

A command is validated against the aggregate’s current state.
The aggregate emits one or more events.
Events are appended to the event store atomically.
Current state is rebuilt by replaying events, accelerated by snapshots.
Events are published to projectors and other services.
New views are created by replaying history.
EVENT SOURCING

Advantages

Disadvantages

Complete audit log and time-travel queries.

+ Easily build new read models retroactively.

Steeper learning curve; eventual consistency of views.

+ Natural integration events and debugging by replay.

Event schema evolution is difficult.

+ Append-only writes are fast.

Querying current state requires projections.
Replay and storage cost grows over time.

When to use

When not to use

Ledgers, financial and compliance domains, collaborative systems, and domains needing history or undo.

Simple CRUD, or teams unprepared for versioning and projection complexity.
