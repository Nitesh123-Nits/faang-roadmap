Layered Architecture (N-Tier)

WHAT IS IT?
FUNDAMENTAL IDEA

Code organized into horizontal layers (presentation, application/business, persistence, database), each depending only on the layer below.

Separate concerns by technical responsibility and constrain dependencies to flow downward.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Tangled UI, business and data-access code that is hard to test and change independently.

Popularized by enterprise Java/.NET systems to give large teams a shared, predictable structure.

How it works

A request enters the presentation layer, which validates and maps it.
The presentation layer calls the business layer; it never calls persistence directly.
Business rules run and coordinate one or more repositories.
The persistence layer translates calls into queries.
Results travel back up, mapped to DTOs at each boundary.
“Closed” layers force requests through each tier; “open” layers may be skipped.
LAYERED ARCHITECTURE (N-TIER)

Advantages

Disadvantages

Familiar structure; easy onboarding and clear ownership.
Business logic often depends on persistence design (anemic domain).
Layers can be tested in isolation with mocks.

+ Swapping the UI or persistence technology is

“Sinkhole” anti-pattern: requests pass through layers doing nothing.

localized.

Works well with frameworks like Spring MVC.

When to use

When not to use

CRUD-heavy business applications, teams that want a conventional structure, and systems where the domain logic is moderate.

Rich, evolving domains (prefer Clean/Hexagonal/DDD) and systems where features cut across layers constantly (prefer vertical slices).

Enterprise portals
