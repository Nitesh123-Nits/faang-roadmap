Microservices Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

An application built as independently deployable services, each owning one business capability and its data, communicating over the network.

Align service boundaries with business capabilities so small teams can build, deploy and scale each service autonomously.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Deployment coupling, team contention and uniform scaling in large monoliths.

Popularized by Netflix, Amazon and others as cloud, containers and DevOps made independent services operable.

How it works

Clients call an API gateway, which routes to a service.
A service executes within its own bounded context and data store.
Synchronous calls are used for queries that need immediate answers.
State changes are published as events for other services.
Each service is built, deployed and scaled independently by its team.
Service discovery, tracing and resilience patterns keep the mesh operable.

Advantages

Disadvantages

Independent deployment and scaling per capability.

+ Fault isolation and technology freedom.

Distributed-system complexity: latency, partial failure, eventual consistency.

+ Team autonomy aligned to the domain.

Heavy operational load: CI/CD, observability,

discovery, security.

+ Enables targeted resilience and ownership.

Cross-service transactions need sagas.
Poor boundaries create a distributed monolith.

When to use

When not to use

Large systems with multiple teams, distinct scaling profiles, and high release frequency, where the organization has strong DevOps maturity.

Small teams, unclear domain boundaries, low operational maturity, or when a modular monolith would suffice.
