Distributed Transaction Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Coordinating a transaction across multiple resources or services, classically with two-phase commit (2PC), so all commit or all abort.

A coordinator asks all participants to prepare; if every one agrees, it instructs them to commit, otherwise abort.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Atomic updates across multiple databases or resource managers.

Enterprise systems (XA, JTA) needed atomicity across databases and message brokers.

Two-phase commit with a coordinator
Client
Domain core

How it works

The application starts a transaction with a coordinator.
Participants perform work and lock resources.
Phase 1: the coordinator asks each to prepare and collects votes.
If all vote yes, Phase 2 instructs everyone to commit.
If any votes no or times out, everyone rolls back.
The coordinator logs decisions to recover from crashes.

Advantages

Disadvantages

Strong atomicity and consistency.

+ Familiar semantics (ACID) across resources.

Blocking: locks held across the network; coordinator failure stalls.

+ Standard support (XA, JTA).

Poor availability and throughput at scale.

+ Simple application programming model.

Not supported by most NoSQL and cloud services.
Tight coupling between participants.

When to use

When not to use

Few trusted resources inside one datacenter where strong atomicity is mandatory.

Microservices at scale, cross-organization calls or high-availability systems — use sagas.

Real-world applications

Key engineering considerations

Banking systems with XA across databases
Legacy JTA applications.

Keep transactions short. Prefer idempotent sagas or the outbox pattern in microservices. Monitor in-doubt transactions and coordinator recovery.
