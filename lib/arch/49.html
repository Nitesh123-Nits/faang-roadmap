MVP (Model-View-Presenter)

WHAT IS IT?
FUNDAMENTAL IDEA

The Presenter holds all presentation logic and updates a passive View through an interface; the View forwards events to the Presenter.

Make the view as dumb as possible so presentation logic can be unit tested without the UI framework.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Untestable UI logic embedded in views and the tight coupling of MVC views to models.

Evolved from MVC for desktop and Android UIs where views were hard to test.

How it works

The user interacts with the view.
The view forwards the event to the presenter.
The presenter calls the model to process the action.
The model returns data or results.
The presenter formats the data for presentation.
The presenter calls methods on the view interface to render it.
MVP (MODEL-VIEW-PRESENTER)

Advantages

Disadvantages

Highly testable presenters using mocked views.
Boilerplate view interfaces and glue code.

+ Clear one-to-one presenter/view relationship.

Presenters can grow large.
View is simple and replaceable.
Manual synchronization of state to the view.
No binding framework required.
Lifecycle handling adds complexity.

When to use

When not to use

UIs needing strong testability without data binding frameworks, such as classic Android or desktop apps.

Frameworks with declarative binding where MVVM reduces glue code.
