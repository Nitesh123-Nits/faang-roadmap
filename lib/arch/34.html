CQRS (Command Query Responsibility Segregation)

WHAT IS IT?
FUNDAMENTAL IDEA

Separate models for writing state (commands) and reading it (queries), often with distinct stores.

Writes and reads have different needs, so optimize each side independently.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

A single model that is poorly suited to both complex business rules and rich, high-volume queries.

Read-heavy systems with complex query needs outgrew a single normalized model.

Separate write and read paths, synchronized by events

How it works

Commands go to a handler that applies business rules to the write model.
The write store is updated transactionally.
Changes are published as events or via change data capture.
A projector updates the denormalized read store.
Queries read only from the read model.
Read and write sides scale independently.
CQRS (COMMAND QUERY RESPONSIBILITY SEGREGATION)

Advantages

Disadvantages

Independent optimization and scaling of reads and writes.
Eventual consistency between sides.
More components and synchronization logic.

+ Simpler, purpose-built models.

Over-engineering for simple domains.

+ Fast queries from denormalized views.

Duplicated data and operational cost.

+ Fits event-driven systems.

When to use

When not to use

Read-heavy systems, complex domain writes with varied read views, and reporting alongside transactions.

Straightforward CRUD, or when users cannot tolerate stale reads and a single model works.

Key engineering considerations

Product catalog with search
Order history views
Banking balance and statement views.

Handle read-your-own-writes explicitly. Make projections idempotent and rebuildable. Monitor replication lag. Do not confuse with Event Sourcing — they combine but are independent.
