Sidecar Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

A helper container deployed alongside the main application container, sharing its lifecycle and network namespace to provide supporting capabilities.

Attach cross-cutting functionality (logging, proxy, config) as a separate process, not as a library.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Embedding polyglot cross-cutting concerns into every application.

Containers and pods made co-located helper processes cheap, isolated and independently versioned.

How it works

The pod starts the app container and its sidecar together.
They share network namespace and volumes.
The app talks to the sidecar over localhost.
The sidecar handles a cross-cutting function (proxying, logging, secrets).
The sidecar communicates with external systems on the app’s behalf.
Both scale and restart together as one unit.
SIDECAR ARCHITECTURE

Advantages

Language-agnostic reuse of cross-cutting logic.

+ Isolation from application code.

Independent upgrades of helper functionality.
Keeps applications simple.

When to use

Service mesh proxies, log/metric agents, config and secret syncers, and legacy integration shims.

Real-world applications

Envoy proxy sidecars
Fluent Bit log shippers
Dapr runtime
Vault agent.

Disadvantages

Extra resource consumption per instance.
Lifecycle and startup-ordering complexity.
Added network hop and debugging surface.
Many sidecars multiply operational overhead.

When not to use

When a shared library is simpler and the system is single-language.

Key engineering considerations

Set resource limits for sidecars. Order startup and shutdown explicitly. Monitor sidecar health along with the app.
