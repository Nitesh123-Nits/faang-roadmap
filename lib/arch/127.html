E-Commerce Platform

A high-traffic retail platform with a browse-heavy read path and a transactional checkout path. It shows how a modular catalog and search side coexists with saga-coordinated order flow.

MAJOR SERVICES & COMPONENTS
COMMUNICATION MECHANISMS

Catalog, Search, Cart, Order, Payment, Inventory, Fulfilment, Notification, Recommendations; API gateway with web and mobile BFFs.

Synchronous REST/gRPC for browse and cart; Kafka events for order lifecycle and search indexing; saga for checkout across Order, Payment and Inventory.

DATA STORAGE ARCHITECTURE
EXTERNAL DEPENDENCIES

PostgreSQL for orders and payments (ACID); MongoDB for flexible catalog; Redis for carts and caching; Elasticsearch for search; object storage and CDN for images.

Payment gateway (PSP), shipping carriers, tax service, email/SMS providers, fraud service.

CHOSEN ARCHITECTURAL STYLE
WHY THIS ARCHITECTURE WAS SELECTED

Microservices with event-driven integration, CQRS for search/catalog reads and database-per-service.

Browse traffic and checkout have opposite needs: reads scale via cache and search indexes, while checkout needs consistency and auditability. Independent services let teams release and scale catalog separately from payment.

KEY TRADE-OFFS

Eventual consistency between catalog and search; saga compensation complexity; more infrastructure than a monolith. A modular monolith is a valid start before the traffic and team size justify this split.
