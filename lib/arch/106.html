Master–Slave / Primary–Replica Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

One primary node handles writes and propagates changes to replica nodes, which typically serve reads and act as failover standbys.

A single writer simplifies consistency; replicas scale reads and provide redundancy.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Read scaling and availability for databases and services with a clear single source of truth.

Simple, predictable replication underlies MySQL, PostgreSQL and Redis setups (the term “primary– replica” replaces “master–slave”).

How it works

The application sends writes to the primary.
The primary commits and records changes in a replication log.
Replicas apply the log asynchronously or synchronously.
Reads are routed to replicas to reduce primary load.
If the primary fails, a replica is promoted.
Replication lag can make replica reads stale.

Advantages

Disadvantages

Simple consistency model with one writer.
Write throughput is limited to one node.

+ Read scalability and redundancy.

Replication lag causes stale reads.
Replicas support backups and analytics without affecting the primary.
Failover can lose recent writes (async) or add latency (sync).

+ Well-supported in most databases.

Promotion and split-brain risks.

When to use

When not to use

Read-heavy workloads and databases needing simple, strongly ordered writes.

Write-heavy or multi-region active-active write needs (consider sharding or multi-primary).
