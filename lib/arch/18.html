II.03

Onion Architecture

WHAT IS IT?
FUNDAMENTAL IDEA

Layered rings around a domain model: domain model, domain services, application services, then infrastructure and UI on the outside.

Make the domain model the center, with every outer ring depending inward, so infrastructure becomes a replaceable detail.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Traditional layering where the domain depends on the data layer.

Jeffrey Palermo (2008) inverted the dependency between business and data access in layered designs.

How it works

The UI calls an application service.
The application service coordinates domain services and entities.
Domain code expresses rules using the domain model only.
Repository interfaces are defined in the domain ring.
Infrastructure implements those interfaces and is wired at startup.
Dependency injection keeps the center free of outer references.

Advantages

Disadvantages

Domain is independent of persistence and frameworks.
More layers and indirection than classic layering.
Requires dependency inversion discipline.

+ Strong testability of core logic.

Mapping between rings adds boilerplate.

+ Clear separation of domain and application services.

Ring boundaries can blur without enforcement.

+ Natural fit for DDD.

When not to use
