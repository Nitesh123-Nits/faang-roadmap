Hexagonal Architecture (Ports and Adapters)

WHAT IS IT?
FUNDAMENTAL IDEA

An application core surrounded by ports (interfaces) with adapters that connect it to drivers (UI, tests) and driven systems (DB, messaging).

Treat every external interaction — inbound or outbound — as an adapter plugged into a port owned by the core.

PROBLEM IT SOLVES
WHY IT WAS INTRODUCED

Business logic coupled to specific technologies and hard to test without infrastructure.

Alistair Cockburn introduced it (2005) to make applications equally drivable by users, programs, tests and batch jobs.

How it works

A driving adapter (REST, listener, test) calls an inbound port.
The domain service executes business logic inside the core.
When it needs infrastructure, it calls an outbound port.
A driven adapter implements that port (JPA, Kafka, HTTP client).
Swapping adapters needs no change to the core.

Tests drive the same inbound ports with fake driven adapters.

HEXAGONAL ARCHITECTURE (PORTS AND ADAPTERS)

Advantages

Disadvantages

Technology-agnostic core, easy to swap infrastructure.
Extra interfaces and mapping layers.
Port design requires judgment.

+ Uniform testing through ports.

Can be overkill for trivial services.

+ Clear inbound/outbound boundaries.

Team must hold the discipline.

+ Works well with DDD and event-driven edges.

When to use

When not to use

Services with meaningful domain logic, many integrations, or the need to test without infrastructure and swap technologies.

Simple pass-through APIs or short-lived scripts where ports add cost without value.

Real-world applications

Key engineering considerations

Integration-heavy order management

Name ports by business intent, not technology. Keep adapters thin. Verify with architecture tests that core packages never import adapters.
