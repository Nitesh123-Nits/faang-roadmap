Scheduling with Priority Queue

Greedy choices made, and reconsidered, with a heap of what is available.

A. Pattern Overview

Many scheduling and resource problems have the same skeleton: sweep over time (or a sorted order); at each step add what became available to a priority queue; then take the best available item. A second flavour defers a decision and undoes it later ("use a ladder now, and if I run out, retroactively swap the smallest climb to bricks"). The heap holds exactly the choices you may still revise.

KEY IDEA

"Decide now, fix later." When a greedy choice can be revisited cheaply, make the optimistic choice, push it in a heap, and undo the least valuable commitment only when a constraint breaks. The heap root is the best candidate to undo.

B. When to Recognize This Pattern

Pattern Recognition Signals

Tasks with start (enqueue) times and durations or deadlines and a rule for picking the

next one.

"Maximise the number of courses / jobs / events" under deadlines: heap of durations, drop the longest.
Two resources, one scarce (ladders vs bricks, fuel stops vs distance): defer the use of the

scarce resource.

"Pick at most k" with a score that depends on the minimum (or a threshold) of the chosen set: sort by the threshold, keep a size-k heap.
Simulation of a machine that repeatedly chooses the "next best" item.
ONE-LINE TEST

Time or threshold sweep plus "best available" or "undo the worst": sorted input + PriorityQueue.

C. Core Intuition with Illustrations

Furthest building: ladders absorb the biggest climbs

Heights [4, 2, 7, 6, 9, 14, 12], 5 bricks, 1 ladder. Every positive climb enters a min-heap of ladder-covered climbs. When the heap has more entries than ladders, the smallest climb is moved from a ladder to bricks. Climbs are processed left to right but the final assignment is as if we had known all climbs in advance: the largest ones get the ladders.

StepClimbResourceLadder climbsBricks left

1 → 25ladder[5]5

3 → 43bricks for 3 (smallest)[5]2
4 → 55bricks for 5 (smallest); stuck[5]-3

We run out of bricks at step 4 → 5, so the furthest building is index 4.

Why the exchange is safe

At any moment the set of climbs covered by ladders should be the ladders largest climbs seen so far (a ladder is worth most on a tall climb). The heap maintains exactly that set. If it overflows, evicting its smallest member is optimal by an exchange argument: swapping a smaller climb onto bricks never uses more bricks.

Single-threaded CPU: sweep by time, pick the shortest

Sort tasks by enqueue time. When the CPU is free, add every task with enqueue ≤ time to a

min-heap ordered by (duration, index) and run the top one to completion. If the heap is empty, jump time to the next enqueue time.

Tasks [enqueue, duration] = [1,2], [2,4], [3,2], [4,1]: execution order [0, 2, 3, 1].

Course Schedule III: keep many, drop the longest

Sort courses by deadline and take them one by one. After adding a course, if the total time exceeds its deadline, remove the longest course taken so far (possibly the one just added). Dropping swaps one course for a shorter-or-equal one, so the number of kept courses never decreases and the kept set always fits.

Maximum courses: 3.

Refuel stops: spend fuel you passed, retroactively

Drive as far as the current fuel allows, pushing every station you pass into a max-heap of fuel amounts. When you cannot reach the next station or the target, "retroactively" refuel at the passed station with the most fuel and count one stop. This is a greedy on which past stop to use, not when.

E. Java Implementation

Furthest building, CPU, max performance, refuel stops, courses

PQScheduling.java: LeetCode 1642, 1834, 1383, 871, 630
import java.util.*;

/** Ch 63: priority-queue scheduling; LeetCode 1642, 1834, 1383, 871, 630. */
public class PQScheduling {
    private static final long MOD = 1_000_000_007L;

    /** LeetCode 1642: furthest building reachable with bricks and ladders. */
    public static int furthestBuilding(int[] heights, int bricks, int ladders) {
        // climbs covered by ladders
        PriorityQueue<Integer> climbs = new PriorityQueue<>();
        for (int i = 0; i + 1 < heights.length; i++) {
            int climb = heights[i + 1] - heights[i];
            if (climb <= 0) continue;
            climbs.offer(climb);
            // smallest climb uses bricks
            if (climbs.size() > ladders) bricks -= climbs.poll();
            if (bricks < 0) return i;
        }
        return heights.length - 1;
    }

    /** LeetCode 1834: single-threaded CPU; tasks[i] = {enqueue, duration}. */
    public static int[] getOrder(int[][] tasks) {
        int n = tasks.length;
        Integer[] byStart = new Integer[n];
        for (int i = 0; i < n; i++) byStart[i] = i;
        Arrays.sort(byStart, Comparator.comparingInt(i -> tasks[i][0]));
        PriorityQueue<int[]> ready = new PriorityQueue<>((a, b) ->
                a[0] != b[0]
                    ? Integer.compare(a[0], b[0])
                    : Integer.compare(a[1], b[1]));
        int[] order = new int[n];
        long time = 0;
        int next = 0, out = 0;
        while (out < n) {
            if (ready.isEmpty() && time < tasks[byStart[next]][0])
                time = tasks[byStart[next]][0];
            while (next < n && tasks[byStart[next]][0] <= time) {
                int id = byStart[next++];
                // shortest, then smallest index

Java 17+

                ready.offer(new int[] {tasks[id][1], id});
            }
            int[] cur = ready.poll();
            order[out++] = cur[1];
            time += cur[0];
        }
        return order;
    }

    /**
     * LeetCode 1383: max (sum of speeds) * (min efficiency) over at most k
     * engineers.
     */
    public static int maxPerformance(int n, int[] speed, int[] efficiency, int k) {
        Integer[] by = new Integer[n];
        for (int i = 0; i < n; i++) by[i] = i;
        Arrays.sort(by, (a, b) -> Integer.compare(efficiency[b], efficiency[a]));
        // speeds, smallest on top
        PriorityQueue<Integer> team = new PriorityQueue<>();
        long sum = 0, best = 0;
        for (int id : by) {
            team.offer(speed[id]);
            sum += speed[id];
            if (team.size() > k) sum -= team.poll();            // drop the slowest
            // efficiency[id] is the minimum
            best = Math.max(best, sum * efficiency[id]);
        }
        return (int) (best % MOD);
    }

    /**
     * LeetCode 871: fewest refuelling stops to reach target; stations = {position,
     * fuel}.
     */
    public static int minRefuelStops(int target, int startFuel, int[][] stations) {
        PriorityQueue<Integer> passed =
                new PriorityQueue<>(Comparator.reverseOrder());
        long reach = startFuel;
        int stops = 0, i = 0;
        while (reach < target) {
            while (i < stations.length && stations[i][0] <= reach)
                passed.offer(stations[i++][1]);
            if (passed.isEmpty()) return -1;                    // stuck
            // refuel retroactively at the biggest
            reach += passed.poll();
            stops++;
        }
        return stops;
    }

    /** LeetCode 630: most courses finishable; courses[i] = {duration, lastDay}. */
    public static int scheduleCourse(int[][] courses) {
        int[][] sorted = courses.clone();
        Arrays.sort(sorted, Comparator.comparingInt(c -> c[1]));
        PriorityQueue<Integer> taken =
                new PriorityQueue<>(Comparator.reverseOrder());
        long time = 0;
        for (int[] c : sorted) {
            taken.offer(c[0]);
            time += c[0];
            // drop the longest course
            if (time > c[1]) time -= taken.poll();
        }
        return taken.size();
    }
}

TIME O(n log n)

SPACE O(n)

A sort plus at most one heap operation per item. getOrder jumps over idle time instead of ticking, maxPerformance multiplies in long before taking the modulus, and minRefuelStops tracks the reach as a long.

F. Detailed Dry Run

For the building example the climbs are 5 (step 1→2), 3 (step 3→4), 5 (step 4→5); descents are free. The first climb 5 sits on the ladder. The climb 3 overflows the heap, so 3 is moved to bricks (5 − 3 = 2 left). The next climb 5 overflows again; the smallest in the heap is 5 and moving it to bricks leaves 2 − 5 = −3 < 0. We cannot cross at index 4, so the answer is 4.

For the CPU example the order is task 0 at time 1 (finishes 3), then at time 3 the ready tasks are 1 (duration 4) and 2 (duration 2): the shorter task 2 runs (finishes 5); task 3 (duration 1) is then ready and runs before task 1 (duration 4). Order [0, 2, 3, 1].

G. Variations of the Pattern

Maximum performance of a team (1383)

Sort engineers by efficiency descending. The efficiency under consideration is the minimum of the team, so keep the k fastest speeds seen so far in a min-heap and multiply

the running sum by the current efficiency. Result modulo 10⁹ + 7, but compare unreduced

values.

Minimum cost to hire k workers (857)

Sort by wage-to-quality ratio; the current ratio is the maximum, so keep the k smallest qualities in a max-heap and cost = qualitySum × ratio.

Meeting rooms with allocation (2402, 253)

Heap of busy rooms by end time plus heap of free rooms by index (Chapter 66).

Server and task assignment (1882)

Two heaps: free servers by (weight, index), busy servers by (free time, weight, index); advance time to the earliest completion when nothing is free.

Reorganize and cooldown schedules

Task Scheduler and Reorganize String use a max-heap of counts plus a cooldown queue (Chapter 69).

J. Interview Tips

INTERVIEW

Describe the greedy invariant first ("ladders on the biggest climbs so far") and only then the heap; the heap is just how you maintain the set.

Name the exchange argument in one sentence; these problems are easy to get "almost right" with the wrong heap direction.

Show a tiny counter-example for the naive greedy (e.g. using bricks first), then fix it with the heap.

Follow-ups: online arrival of tasks; preemptive scheduling (shortest remaining time first); priorities with aging; many workers instead of one CPU; real-time constraints.
Edge cases: all tasks identical, enqueue times equal, a task that is ready only after a long idle gap, zero ladders, zero bricks, an unreachable target.

CHAPTER SUMMARY

Scheduling with a priority queue: sweep over time or a sorted key, add newly available items, take the best; or make an optimistic choice and undo the cheapest-to-undo one when a constraint breaks.

Furthest Building: ladders belong on the largest climbs, so keep a min-heap of ladder climbs and spill the smallest to bricks.

CPU / IPO: sort by enqueue (or capital), heap by duration (or profit); jump over idle time.

Courses III / Refuel: retroactive undo with a max-heap: drop the longest course, spend the biggest passed fuel.

Performance / Hire K: sort by the threshold quantity, keep a size-k heap of the best values; multiply in long.
