Peak Finding and Bitonic Search

Follow the slope: a local comparison tells you which side must contain a peak.

A. Pattern Overview

Binary search does not need a sorted array; it needs a local test that tells you which half to keep. In a peak-finding problem the test is the slope at mid: if nums[mid] < nums[mid + 1] the ground rises to the right, so a peak must exist on the right (the array eventually ends, treating nums[n] = −∞); otherwise a peak exists at mid or to its left. A bitonic (mountain) array increases strictly to one peak and then decreases strictly; it is the special case with exactly one peak, and searching it means find the peak, then binary search each side.

KEY IDEA

Slope rule: compare nums[mid] with its neighbour nums[mid + 1] and move toward the higher neighbour. A peak is guaranteed in that direction because the boundary is treated as −∞.

B. When to Recognize This Pattern

Pattern Recognition Signals

"Find a peak element" where any peak is acceptable and neighbours differ (nums[i] != nums[i+1]).
The array is described as a mountain, bitonic, "increases then decreases", or has a single

maximum.

Required complexity O(log n) for a non-sorted array: the only structure available is the slope.
The comparison of mid with its neighbour can reveal a direction (unimodal functions,

hill climbing in one dimension).

Limited access (a MountainArray interface with a call budget): you must reuse reads carefully.
DECISION RULE

Unsorted + O(log n) + "peak / maximum / local" → compare with the neighbour, not with a target. For a unimodal function you can also use ternary search, but the neighbour comparison on integers is simpler and exact.

C. Core Intuition with Illustrations

Figure 32. Rising slope: peak to the right. Falling slope: the peak is mid or to the left. The range always contains a peak.

INTUITION

Why a peak must exist in the kept half. Suppose nums[mid] < nums[mid + 1]. Walk right from mid + 1: either the values keep rising until the array ends (the last element is a peak because nums[n] = −∞), or they eventually fall, and the point where they first fall is a peak. Either way, a peak lives in [mid + 1, hi]. The same argument works to the left when the slope falls.

D. Brute Force to Optimal Solution

Example: Find in Mountain Array (LeetCode 1095)

Brute force: read every element: O(n) calls, which exceeds the allowed budget of 100 get() calls for n up to 10⁴.
Find the peak: binary search with the slope rule: about log₂ n iterations, 2 reads each.
Search the ascending side [0, peak] with ordinary binary search. If found, return immediately: the smaller index wins.
Otherwise search the descending side [peak + 1, n − 1] with the comparison flipped.
Total: three binary searches, O(log n) time and reads, O(1) space.

E. Java Implementation

Find Peak Element / Peak Index in a Mountain Array

FindPeakElement.java — LeetCode 162 / 852

Java 17+

/** LeetCode 162 - Find Peak Element, and LeetCode 852 - Peak Index in a Mountain Array. */
public class FindPeakElement {

    /**
     * Returns the index of ANY peak: nums[i] > both neighbours, with nums[-1] = nums[n] =
     * -infinity.
     */
    public static int findPeakElement(int[] nums) {
        int lo = 0;
        int hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] < nums[mid + 1]) {
                lo = mid + 1;           // rising slope: a peak must exist to the right
            } else {
                // falling (or at a peak): a peak exists at mid or to the left
                hi = mid;
            }
        }
        return lo;
    }
}

TIME O(log n)

SPACE O(1)

Loop condition lo < hi guarantees mid + 1 is in range. Returns a peak, not necessarily the largest one (for LC 162).

Find in Mountain Array

FindInMountainArray.java — LeetCode 1095 (MountainArray interface supplied by the judge)

Java 17+

/** Provided by the judge. get() calls are limited, so avoid repeating them. */
interface MountainArray {
    int get(int index);
    int length();
}

/** LeetCode 1095 - Find in Mountain Array: find the peak, then binary search each side. */
public class FindInMountainArray {

    public static int findInMountainArray(int target, MountainArray arr) {
        int n = arr.length();
        int peak = findPeak(arr, n);
        int left = searchAscending(arr, target, 0, peak);          // increasing side first:
        if (left != -1) return left;                               // the smaller index wins
        return searchDescending(arr, target, peak + 1, n - 1);
    }

    private static int findPeak(MountainArray arr, int n) {
        int lo = 0;
        int hi = n - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (arr.get(mid) < arr.get(mid + 1)) lo = mid + 1; else hi = mid;
        }
        return lo;
    }

    private static int searchAscending(MountainArray arr, int target, int lo, int hi) {
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            int value = arr.get(mid);
            if (value == target) return mid;
            if (value < target) lo = mid + 1; else hi = mid - 1;
        }
        return -1;
    }

    private static int searchDescending(MountainArray arr, int target, int lo, int hi) {
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            int value = arr.get(mid);
            if (value == target) return mid;
            if (value > target) lo = mid + 1; else hi = mid - 1;    // comparison is flipped
        }
        return -1;
    }
}

TIME O(log n) reads

SPACE O(1)

Search the ascending side first: if the target appears on both sides, the lower index is required. The descending search flips the comparison.

G. Variations of the Pattern

Peak Index in a Mountain Array (LeetCode 852)

The same method. Because the mountain has a single peak, the answer is unique and also the maximum value: FindPeakElement.findPeakElement solves it unchanged.

Search in a Mountain Array with a read budget

FindInMountainArray above performs about 3 · log₂ n reads. To cut reads further, cache

get(mid) and get(mid + 1) in local variables instead of re-reading.

Find a peak in a 2D grid (LeetCode 1901)

Pick the middle column, find its row maximum, compare with the left and right neighbours, and move toward the larger neighbour (a peak must exist there). That halves the columns each step: O(m log n).

Unimodal functions and ternary search

For a unimodal real function, ternary search narrows [lo, hi] by thirds. For integer arrays prefer the neighbour comparison: it is exact, simpler, and needs one comparison per step. Related hard problem: Median of Two Sorted Arrays (LeetCode 4) binary searches the partition point of the shorter array in O(log(min(m, n))); it uses the same "local test decides direction" reasoning.

Equal neighbours break the guarantee

If nums[i] == nums[i+1] is allowed (plateaus), the slope test can be ambiguous and the worst case degrades to O(n). LeetCode 162 guarantees distinct neighbours; confirm that in an interview.

J. Interview Tips

INTERVIEW

Prove the direction rule in one sentence: "moving toward the larger neighbour always keeps a peak because the array ends at −∞".

Explain why hi = mid: the current element may itself be the peak.

Clarify whether adjacent values can be equal and whether any peak is acceptable.

Follow-ups: 2D peak, return the global maximum (not just any peak: use the mountain

structure), mountain with duplicates, bitonic array that is rotated.

Edge cases: n = 1, n = 2, strictly increasing (peak at the end), strictly decreasing (peak at 0), peak at the first or last index.

CHAPTER SUMMARY

A local comparison can drive binary search even without sorting: compare nums[mid] with nums[mid + 1] and move toward the larger side.

Use lo < hi, hi = mid on a falling slope, lo = mid + 1 on a rising slope; the range always contains a peak.

Mountain search = find the peak, search the ascending side first, then the descending side with the comparison flipped.

Plateaus remove the guarantee; confirm the constraints.
