M1

Pattern Recognition Masterclass

How to look at an unfamiliar problem and name the pattern before writing a line of code.

Why recognition beats memorisation

Parts I to XII taught 107 patterns one at a time. In an interview nobody announces the chapter. You get a paragraph of English, a few constraints and a clock. This masterclass is the missing step: a repeatable procedure that turns the statement and the constraints into a short list of candidate patterns, then uses cheap tests to choose between them. Every rule below is tied to the chapter where the pattern is taught and proved.

THE FUNNEL

Recognition is a funnel, not a flash of insight: constraints shrink the complexity budget, keywords suggest families, and a one-line test per family confirms or rejects it. Spend the first five minutes of any problem on this funnel.

Read the constraints first

The constraint line is the most informative sentence in the problem. It tells you which complexity the author expects, and therefore which family of algorithms is allowed. A judge or interviewer typically allows about 10⁸ simple operations per second in Java; the chart shows how quickly each growth rate runs out of room.

WATCH OUT

A yes is a hypothesis, not a verdict. Confirm it with the one-line test in the section that follows before you commit to coding. Two patterns often fit, and the later sections explain how to choose.

Can sorting simplify the problem?

Sorting costs O(n log n), which is affordable for any n up to about 10⁶. It is worth doing when the answer does not depend on the original order of the elements, because sorting then turns a global question into a local one: equal items become adjacent, pairs can be found from both ends, and overlapping ranges become consecutive.

A hash table answers "have I seen this key, and what did I store for it?" in expected O(1). It replaces an inner search loop, so the telltale sign is a nested loop whose inner loop only looks something up.

ONE-LINE TEST

Sorted (or sortable) input, a pair or triple condition, and an O(n²) brute force whose inner loop could be replaced by "move a pointer".

When to use a sliding window

A sliding window maintains a contiguous range [left, right] and a summary of it (a count, a sum, a map) that can be updated in O(1) when one element enters or leaves. It is correct only when validity is monotone in the window: if a window is valid, a smaller window inside it is valid (for "at most" conditions), or if it is invalid, a larger window containing it is invalid.

THE MOST COMMON WRONG TURN

Negative numbers break the window for sum conditions: adding an element can shrink the sum, so shrinking from the left no longer has a clear meaning. Switch to prefix sums plus a hash map (count of subarrays summing to k) or a monotonic deque (shortest subarray with sum at least k, Ch. 8).

When prefix sums are useful

Whenever you see a range sum (or XOR, or count) asked many times, or a condition on sum(i..j), rewrite it as a difference of two prefixes: sum(i..j) = P[j + 1] - P[i]. That converts a two-index question into a one-index question plus a lookup.

When binary search on the answer applies

Binary search does not need a sorted array. It needs a monotone yes/no predicate over a numeric range of candidate answers: once feasible(x) becomes true it stays true as x grows (or the reverse). The answer is the boundary.

Figure 153. A monotone predicate over candidate answers. Binary search finds the first T in O(log range) checks.

Wording: "minimise the maximum", "maximise the minimum", "smallest capacity / speed / time such that ...", "largest x such that ...".
Write feasible(x) as a greedy scan. It usually runs in O(n), so the whole solution is O(n

log range).

Prove monotonicity in one sentence: "if capacity x works, capacity x + 1 also works because ...". If you cannot write that sentence, do not binary search.
Bounds: lo is the smallest conceivable answer (often the maximum single item), hi a

value that is certainly feasible (often the total).

Java
// smallest x in [lo, hi] with ok(x) true; ok must be monotone (Templates.firstTrue)
int l = lo, r = hi + 1;
while (l < r) {
    int mid = l + (r - l) / 2;
    if (ok.test(mid)) r = mid; else l = mid + 1;
}
return l;   // hi + 1 means no feasible value

THE QUICK OVERLAP TEST

Write the plain recursion first and name its parameters. Count how many distinct parameter tuples exist. If that count is polynomial but the call count is exponential, caching the results is the whole solution.

Recognising greedy choices

Greedy is attractive and dangerous: it is the fastest approach when it is correct and a confident wrong answer when it is not. Use three checks, in order.

Shape. The problem asks for a maximum count, a minimum count, or a best ordering, and a sort key suggests itself (end time, deadline, ratio, difference).
Exchange argument. Take any optimal solution that disagrees with the greedy choice at the first step; show you can swap in the greedy choice without making it worse.
Small-case attack. Write the brute force and compare on all inputs up to size 6 or 7 (the tests in this book do exactly that). One counter-example kills the idea.

CHAPTER SUMMARY

Start with the constraints: they fix the intended complexity and exclude whole families.

Match keywords to families, then confirm with a one-line test (monotone? order-independent? repeated states? safe local choice?).

Sort when the answer ignores order; hash when an inner loop only looks something up; window only when validity is monotone and values are non-negative.

Binary search needs a monotone predicate, not a sorted array. DP needs overlapping subproblems and optimal substructure.

Any problem with states and moves is a graph; pick the algorithm from the edge weights.

Say your reasoning out loud: naming the signal and the test is what interviewers score.
