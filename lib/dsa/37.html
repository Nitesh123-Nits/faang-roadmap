LRU and LFU Cache Design

A hash map plus ordered lists: O(1) lookup, O(1) update, O(1) eviction.

A. Pattern Overview

A cache keeps a bounded number of entries and must decide what to evict when it is full. Two policies dominate interviews and real systems:

KEY IDEA

Why two structures? A hash map finds an entry in O(1) but has no order. A list keeps order but needs O(n) to find an entry. Storing the list node in the map gives both: find in O(1), then move or remove that exact node in O(1) because a doubly linked list can unlink itself.

B. When to Recognize This Pattern

Pattern Recognition Signals

"Design a cache with capacity k", "get and put in O(1)", "evict the least recently / frequently used".
"Maintain items in order of recent use" and be able to move any item to the front in O(1).
"Ties broken by recency" inside a frequency class: ordered sets per frequency.
Real-world cues: page replacement, CDN edge caches, database buffer pools, memoisation with bounded memory, @Cacheable with Caffeine (size-bounded, W-TinyLFU).
ONE-LINE TEST

Whenever a statement demands O(1) eviction in a stated order, it is a hash map pointing into an ordered linked structure. The order is the policy.

C. Core Intuition with Illustrations

LRU: most recent at the head, least recent at the tail

Two sentinel nodes (head, tail) remove every empty-list and boundary case. The most recently used entry sits right after head; the eviction victim is tail.prev. get and put on an existing key both unlink the node and re-insert it after head. A put on a new key inserts at the front and, if the cache is over capacity, removes tail.prev and its map entry.

Figure 58. Each operation touches a constant number of pointers; the map locates the node directly.

The three pointer operations
•
unlink(n): n.prev.next = n.next; n.next.prev = n.prev;
addFirst(n): n.next = head.next; n.prev = head; head.next.prev = n; head.next = n;
evict(): lru = tail.prev; unlink(lru); map.remove(lru.key); (so the node must store its key).

Order matters in addFirst: read head.next before overwriting it.

LFU: buckets by frequency

Each key has a count. Keep buckets[f] = the keys with count f, in insertion-into-bucket order (a LinkedHashSet), and minFreq. A touch moves the key from buckets[f] to buckets[f + 1]; if buckets[f] becomes empty and f == minFreq, then minFreq++. Eviction removes the first key of buckets[minFreq] (least frequent, then least recent). A new key has count 1, so minFreq = 1.

Figure 59. Within a bucket the leftmost key is the least recently used; the lowest non-empty bucket is evicted first.

Java ships an LRU: LinkedHashMap

new LinkedHashMap<>(16, 0.75f, true) orders entries by access (the true), and overriding removeEldestEntry to return size() > capacity evicts automatically. It is five lines and perfectly acceptable in production code. In an interview, implement the list yourself first, then mention this.

E. Java Implementation

LRU cache with a hand-written doubly linked list

LRUCache.java: LeetCode 146

Java 17+

import java.util.HashMap;
import java.util.Map;

/**
 * LeetCode 146 - LRU Cache: HashMap for O(1) lookup + doubly linked list for O(1) recency
 * order.
 */
public class LRUCache {

    private static class Node {
        int key, value;
        Node prev, next;
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    // sentinels: MRU after head, LRU before tail
    private final Node head = new Node(), tail = new Node();

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        unlink(n);
        addFirst(n);                                     // a read makes it most recently used
        return n.value;
    }

    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) {
            n.value = value;
            unlink(n);
            addFirst(n);
            return;
        }
        if (map.size() == capacity) {
            Node lru = tail.prev;                        // evict the least recently used
            unlink(lru);
            map.remove(lru.key);
        }
        n = new Node();
        n.key = key;
        n.value = value;
        map.put(key, n);
        addFirst(n);
    }

    private void unlink(Node n) {
        n.prev.next = n.next;
        n.next.prev = n.prev;
    }

    private void addFirst(Node n) {
        n.next = head.next;
        n.prev = head;
        head.next.prev = n;
        head.next = n;
    }
}

TIME O(1) per operation

SPACE O(capacity)

The node stores its key, so eviction can remove the map entry. Sentinels mean unlink and addFirst have no null checks.

LRU cache with LinkedHashMap

LRUCacheLinkedHashMap.java: the idiomatic Java version

Java 17+

import java.util.LinkedHashMap;
import java.util.Map;

/**
 * LRU in six lines: LinkedHashMap in access order, evicting the eldest entry (what Java gives
 * you).
 */
public class LRUCacheLinkedHashMap extends LinkedHashMap<Integer, Integer> {

    private final int capacity;

    public LRUCacheLinkedHashMap(int capacity) {
        // true = access order (get() reorders)
        super(16, 0.75f, true);
        this.capacity = capacity;
    }

    public int getOrDefault(int key) {
        return super.getOrDefault(key, -1);
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        return size() > capacity;                        // called by put() after insertion
    }
}

TIME O(1) per operation

SPACE O(capacity)

accessOrder = true makes get reorder entries. This class is not thread-safe; wrap with Collections.synchronizedMap if needed.

LFU cache with frequency buckets

LFUCache.java: LeetCode 460

Java 17+

import java.util.HashMap;
import java.util.LinkedHashSet;
import java.util.Map;

/**
 * LeetCode 460 - LFU Cache in O(1): a bucket per frequency, each bucket ordered by recency.
 */
public class LFUCache {

    private final int capacity;
    private final Map<Integer, Integer> values = new HashMap<>();
    private final Map<Integer, Integer> counts = new HashMap<>();
    // freq -> keys, oldest first
    private final Map<Integer, LinkedHashSet<Integer>> buckets = new HashMap<>();
    private int minFreq;

    public LFUCache(int capacity) {
        this.capacity = capacity;
    }

    public int get(int key) {
        if (!values.containsKey(key)) return -1;
        touch(key);
        return values.get(key);
    }

    public void put(int key, int value) {
        if (capacity == 0) return;
        if (values.containsKey(key)) {
            values.put(key, value);
            touch(key);
            return;
        }
        if (values.size() == capacity) {
            LinkedHashSet<Integer> lowest = buckets.get(minFreq);
            int victim = lowest.iterator().next();       // least frequent, then least recent
            lowest.remove(victim);
            values.remove(victim);
            counts.remove(victim);
        }
        values.put(key, value);
        counts.put(key, 1);
        buckets.computeIfAbsent(1, f -> new LinkedHashSet<>()).add(key);
        // a new key always has the lowest frequency
        minFreq = 1;
    }

    /** Move key from bucket f to bucket f + 1 and keep minFreq correct. */
    private void touch(int key) {
        int f = counts.get(key);
        LinkedHashSet<Integer> old = buckets.get(f);
        old.remove(key);
        if (old.isEmpty() && f == minFreq) minFreq++;
        counts.put(key, f + 1);
        buckets.computeIfAbsent(f + 1, x -> new LinkedHashSet<>()).add(key);
    }
}

TIME O(1) per operation

SPACE O(capacity)

LinkedHashSet provides insertion order and O(1)

removal by key. Capacity 0 must ignore every put.

G. Variations of the Pattern

LRU with TTL

Store an expiry time per entry. Lazy expiry checks on get; active expiry uses a min-heap (or a timer wheel) keyed by expiry. Redis does both: lazy on access plus a periodic sampling of keys.

Thread-safe LRU

A single lock around get and put is correct but contended, since even a read mutates the list. Production caches (Caffeine, Guava) buffer reads and apply the reordering in batches, trading strict recency for throughput.

Beyond LRU: LRU-K, ARC, and TinyLFU

LRU is vulnerable to scans: one large sequential read flushes the whole cache. LRU-K (evict by the K-th most recent access), ARC (adaptive, balances recency and frequency) and W-TinyLFU (Caffeine's policy: a frequency sketch admits a new key only if it is hotter than the victim) resist scans.

Memoisation with a bound

LinkedHashMap with removeEldestEntry is the standard bounded memo table for recursive functions with large state spaces (Part XI): it keeps the working set and drops cold entries.

Design a cache for a service
Key space and size: estimate entries and bytes; choose capacity by memory, not count.
Consistency: write-through, write-back or cache-aside; invalidate or expire on updates.
Stampede protection: coalesce concurrent misses for one key (a per-key lock or future).
Observability: hit ratio, eviction rate, load latency; a low hit ratio means the policy or the size is wrong.

J. Interview Tips

INTERVIEW

Say the design in one sentence: "a hash map from key to a node of a doubly linked list ordered by recency, with sentinel head and tail". Then draw get(1) moving a node.

Justify the doubly linked list: a singly linked list cannot unlink a node in O(1) without its predecessor.

For LFU, derive the buckets from the failure of the heap: a heap cannot reprioritise in O(1), but frequencies change by exactly +1, so moving between adjacent buckets is O(1).

Follow-ups: make it thread-safe; add TTL; add a delete and a size; support variable-size

values (evict until the byte budget fits); how would you distribute it (consistent hashing, Part XII); what is the hit ratio of LRU on a cyclic scan one larger than the cache (zero).

Edge cases: capacity 1, repeated put of the same key, get of a missing key, put on a full

cache with an existing key, LFU with capacity 0, many keys with equal frequency.

CHAPTER SUMMARY

LRU = HashMap<key, node> + doubly linked list ordered by recency + sentinels. get and put unlink the node and re-insert it at the front; eviction removes tail.prev (and its map entry, so nodes store their key).

A doubly linked list is required so that a node can unlink itself in O(1); the map gives direct access to that node.

LFU = HashMap + LinkedHashSet per frequency + minFreq. A touch moves a key to bucket f + 1; bump minFreq when its bucket empties; a new key resets minFreq = 1; evict the first key of buckets[minFreq].

In Java, LinkedHashMap(accessOrder = true) + removeEldestEntry is a complete LRU in a few lines; know it, but be able to build the list by hand.

In production, add TTL, thread-safety, stampede protection and metrics; scans defeat LRU, which is why policies like W-TinyLFU exist.
