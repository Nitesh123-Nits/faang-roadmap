Distributed Search Engine

Elasticsearch-style cluster

Functional Requirements
Index JSON documents with analysers
Full-text, filter and aggregate queries
Relevance ranking (BM25, boosting)
Near-real-time search (refresh ~1 s)
Horizontal scaling by shards and replicas
Update and delete documents
Snapshot, restore and index lifecycle
Non-Functional Requirements
Latency: p95 < 100 ms for typical queries
Freshness: NRT, doc visible within ~1 s
Scalability: add nodes, rebalance shards online
Availability: replicas serve reads, auto promote
Durability: translog fsync + replicas
Consistency: eventual across replicas, primary-first writes
Operability: rolling upgrades, snapshots

Key design trade-offs

More shards (parallelism) vs overhead per shard

Refresh 1 s (fresh) vs larger interval (throughput)

Replicas (read scale, HA) vs storage cost

Time-based indices (cheap retention) vs one big index

Scaling & Failure Handling R

Node loss: master promotes replicas and rebuilds missing copies on other nodes; searches continue from replicas
Split brain: dedicated master quorum (3 nodes) prevents two masters
Hot shards: custom routing and more shards; time-based indices for logs
Overload: bounded thread-pool queues reject with 429 instead of cascading
