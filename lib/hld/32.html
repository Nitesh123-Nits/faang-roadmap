Payment Processing System

Gateway + ledger

Functional Requirements
Authorise, capture, void and refund payments
Multiple payment methods (card, wallet, bank)
Route to the best PSP with failover
Idempotent requests (safe retries)
Double-entry ledger of money movement
Webhooks from PSPs update payment state
Daily reconciliation and settlement
Non-Functional Requirements
Correctness: exactly-once effect (idempotency + ledger)
Durability: no committed payment is lost (RF=3, sync replication)
Availability: 99.999% for authorisation path
Latency: auth p99 < 2 s (PSP bound)
Security: PCI-DSS, tokenisation, encryption, mTLS
Auditability: immutable ledger and events
Resilience: PSP failover and circuit breakers

Single PSP (simple) vs multi-PSP routing (resilience, cost)

Ledger as source of truth vs payment table only

Strong consistency (SQL) vs throughput (NoSQL)

Scaling &amp; Failure Handling
Retries: client retries with the same Idempotency-Key return the stored response; never charge twice
PSP outage: circuit breaker, then reroute to alternate PSP; payments in unknown state resolved by status poll / webhook
Data safety: ledger append-only with sync replication; no deletes, corrections are new entries
Security: tokenisation, encryption, PCI-scoped network zone
