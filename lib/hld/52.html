Distributed File System

HDFS / GFS style

Functional Requirements
Store very large files across commodity nodes
Sequential streaming reads and appends
Namespace: directories, permissions, quotas
Block replication across racks
Automatic re-replication on failure
Data locality for compute jobs
Snapshots and erasure coding for cold data
Non-Functional Requirements
Throughput: GB/s aggregate sequential I/O
Durability: 3 replicas across 2 racks (or EC)
Availability: NameNode HA failover < 30 s
Scalability: 100 PB, billions of files
Consistency: single-writer, close-to-open
Fault tolerance: disk, node and rack failures are routine
Efficiency: large blocks reduce metadata

Key design trade-offs

3x replication (fast repair) vs erasure coding (1.5x cost)

Large blocks (throughput) vs small-file inefficiency

Write pipeline (chained) vs fan-out

Client asks NameNode for block locations → streams to DN1 → DN2 → DN3 pipeline; ack on all

Read

Client gets block list from NameNode → reads from nearest replica (locality)

Failure

Missed heartbeats → NameNode marks blocks under-replicated → Replicator copies them

Replica placement: 1st on writer rack, 2nd and 3rd on a different rack (survive a rack loss).

All DataNodes send heartbeats every 3 s and block reports to the NameNode.

Scaling & Failure Handling

R
NameNode failure: standby has near-current state from JournalNodes; ZKFC fences old active and promotes within seconds
DataNode / rack loss: blocks re-replicated from surviving copies; rack-aware placement keeps at least one replica alive
Corruption: CRC on read and background block scanner; corrupt replicas replaced
NameNode memory: limit small files, use federation or archival to scale metadata
