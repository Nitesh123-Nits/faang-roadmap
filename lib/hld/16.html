Non-Functional Requirements
Availability: AP by default, writes succeed with nodes down
Latency: single-digit ms reads and writes
Scalability: linear scale-out, no central master
Durability: WAL + RF=3 across AZs
Consistency: tunable (R + W > N for strong)
Partition tolerance: keep serving, repair later
Operability: online rebalancing, rolling upgrades

Back-of-envelope: Quorum: N=3, W=2, R=2 gives R + W > N, so reads see the latest committed write (strong); W=1, R=1 favours speed.

Key design trade-offs

AP (always writable) vs CP (single value)

Vector clocks (precise conflicts) vs last-write-wins (simple)

LSM (write-optimised) vs B-tree (read-optimised)

Quorum read repair vs async repair only

Write

Client → Coordinator → hash ring → N replicas; ack after W confirm (WAL + MemTable)

Read

Coordinator → R replicas → newest version wins → read repair if stale

Failure

Gossip marks node down → hinted handoff stores writes → anti-entropy repairs on return

Replicas are the next N distinct nodes clockwise on the ring, spread across AZs.

Conflicts: vector clocks detect concurrent writes; client or LWW resolves.

Scaling & Failure Handling R

Node failure: gossip detects it, hinted handoff buffers writes, anti-entropy repairs on rejoin
AZ failure: replicas spread over 3 AZs, so quorum of 2 survives one AZ loss
Scaling: add node, take vnode tokens, stream only affected ranges, no downtime
Hot keys: client-side caching, key salting, replica read balancing
