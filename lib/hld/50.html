Metrics Monitoring System

Prometheus / Datadog style

Functional Requirements
Collect metrics from services (pull and push)
Store time series with labels
Query with a rich language (rates, aggregates)
Dashboards and ad-hoc exploration
Alert rules with grouping and routing
Recording rules for expensive queries
Long-term retention with downsampling
Non-Functional Requirements
Ingest: 5M samples/s, 10M active series
Query latency: p95 < 1 s for dashboard panels
Availability: alerting path highly available (99.99%)
Durability: WAL + RF=3, no gaps during node failure
Scalability: shard by series hash
Cost: compress ~1.3 B/sample, downsample old data
Cardinality: guard against label explosions

Key design trade-offs

Pull scraping (simple discovery) vs push (short-lived jobs)

Kafka buffer (durable) vs direct write (low latency)

Sharded TSDB with RF=3 vs single Prometheus + federation

High cardinality labels vs cost

Scaling & Failure Handling R

Ingester failure: RF=3 with WAL replay; hash ring rebalances series; queries read from replicas
Alert path: Alert Manager clustered with gossip; deduplication across replicas
Cardinality bombs: per-tenant series limits, ingestion drops with clear errors
Query load: frontend caching and limits; recording rules for heavy dashboards
