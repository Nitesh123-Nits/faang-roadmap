Functional Requirements
Publish messages to topics (partitioned)
Consume with consumer groups and offsets
Ordering guaranteed within a partition
Retention by time / size; log compaction
Replay from any offset
Delivery semantics: at-least-once, optional exactly-once
Topic, partition and ACL administration
Non-Functional Requirements
Throughput: millions of msgs/s, sequential disk I/O
Latency: single-digit ms produce, end-to-end < 50 ms
Durability: acks=all with min.insync.replicas=2
Availability: leader failover in seconds
Scalability: add partitions and brokers online
Ordering: per partition key
Retention: days locally, months in tiered storage

Key design trade-offs

Pull (consumer pace, batching) vs push (low latency)

acks=all (durable) vs acks=1 (faster)

More partitions (parallelism) vs metadata / recovery cost

Exactly-once (idempotent + txn) vs at-least-once + dedupe

Consume

Failure

Controller elects a new leader from ISR; consumer group rebalances; old segments tier to S3

ISR: leader waits for in-sync replicas; min.insync.replicas = 2.

Broker failure: controller promotes an in-sync follower; producers retry to the new leader (idempotent)
AZ failure: replicas rack-aware across 3 AZs; min.insync.replicas=2 keeps writes safe with one AZ down
Slow consumers: lag alerts; retention keeps data so consumers catch up; DLQ for poison messages
Unclean election: disabled by default to avoid data loss; availability traded for durability
