Functional Requirements
Tenant onboarding, plans and feature flags
Tenant-aware authentication (SSO, SAML)
Data isolation per tenant
Per-tenant quotas and rate limits
Usage metering and billing
Custom domains and branding
Tenant admin, audit logs and data export
Non-Functional Requirements
Isolation: no cross-tenant data access (RLS, schema, or DB)
Fairness: noisy neighbour cannot degrade others
Availability: 99.95% per tenant, cell-based blast radius
Scalability: 50K small tenants + few huge ones
Compliance: data residency, encryption, audit
Cost efficiency: pooled by default, silo on demand
Operability: per-tenant observability and migration

Back-of-envelope: Cell architecture: tenants are assigned to cells (e.g. 5K tenants each); a cell failure affects 10% of tenants, not all.

Key design trade-offs

Pooled (cheap, shared) vs siloed (isolated, costly)

Row-level security (simple) vs schema per tenant (stronger)

Cell-based deploys (small blast radius) vs one global stack

Per-tenant limits (fair) vs global limits (simple)

Noisy neighbour: per-tenant rate limits and connection pools; heavy tenants moved to silos or dedicated cells
Blast radius: cell-based deployment; a bad deploy or failure affects only that cell's tenants
Data leaks: tenant context set at the gateway, enforced by RLS in the DB, covered by automated isolation tests
Migration: tenant moves between pooled / silo with dual-write + cutover; registry updated atomically
