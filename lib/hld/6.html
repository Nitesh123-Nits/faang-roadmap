Rate Limiter

API throttling

Functional Requirements
Limit requests per user, API key, IP or tenant
Support multiple algorithms (token bucket, sliding window)
Configurable rules per endpoint and plan
Return 429 with Retry-After and limit headers
Allow burst traffic up to a configured cap
Update rules without redeploying
Expose usage and throttling metrics
Non-Functional Requirements
Latency: decision adds < 2 ms p99
Availability: limiter failure must not take the API down (fail-open by default)
Accuracy: distributed counters are atomic, small overshoot tolerated
Scalability: 175K checks/s, shard counters by client key
Consistency: eventual for rules, atomic for counters
Fairness: one noisy tenant cannot starve others
Security: keys derived from authenticated identity

Key design trade-offs

Token bucket (bursts) vs sliding window (smooth, costlier)

Central Redis (accurate) vs local counters (fast, approximate)

Fail-open (availability) vs fail-closed (protection)

Gateway middleware vs standalone service

Allowed Request

Client → LB → Gateway → Limiter → Redis (atomic bucket) → forward to Backend

Rejected Request

Redis bucket empty → Limiter says deny → Gateway returns 429 + Retry-After

Rule Update

Admin → Rules Service → Rules Store → pushed to limiter local cache

On reject: HTTP 429 + Retry-After + X-RateLimit-Limit / Remaining / Reset.

Algorithms: token bucket, sliding window counter, fixed window. Lua script makes check + decrement atomic.

Fail-open if Redis is unreachable; local in-memory fallback limits.

Scaling & Failure Handling R

Scale: shard buckets by client key; add primaries and rebalance slots online
Replication: one async replica per shard; failover promotes in seconds
Redis down: fail-open with per-node in-memory limits; alert on fallback rate
Hot keys: split a noisy client key into N sub-buckets, sum on read
