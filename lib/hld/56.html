Event-Driven Architecture

Choreographed microservices

Functional Requirements
Services publish domain events (OrderPlaced, PaymentCaptured)
Independent consumers react asynchronously
Schema evolution without breaking consumers
Reliable publish with the outbox pattern
Retry, dead-letter and replay
Event archive for audit and reprocessing
Saga choreography across services
Non-Functional Requirements
Decoupling: producers do not know consumers
Delivery: at-least-once; consumers are idempotent
Ordering: per aggregate key within a partition
Throughput: 100K events/s, linear with partitions
Resilience: consumer outages do not block producers
Evolvability: backward / forward compatible schemas
Traceability: correlation id on every event

Key design trade-offs

Choreography (loose) vs orchestration (visible flow)

Event notification (thin) vs event-carried state (fat)

Outbox + CDC (reliable) vs dual write (risky)

Schema registry (safe evolution) vs ad hoc JSON

Publish

Service writes state + outbox row in one DB transaction → Outbox Relay (CDC) → Event Bus

React

Each consumer group processes the event idempotently and updates its own datastore

Recover

Failures retry, then go to DLQ; events replayed from the archive or by offset reset

Outbox: state change and event are one DB transaction; the relay publishes later, so no dualwrite gap.

Scaling &amp; Failure Handling
Consumer down: events wait in Kafka; consumer catches up from its committed offset; producers unaffected
Duplicates: at-least-once delivery + processed_events table makes handlers idempotent
Poison events: bounded retries with backoff, then DLQ and alert; replay after fix
Breaking schema: registry rejects incompatible versions; consumers upgraded first
