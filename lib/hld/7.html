Distributed Cache

Redis-style cluster

Functional Requirements
GET, SET and DELETE a key
Per-key TTL expiry
Eviction when memory is full (LRU / LFU)
Atomic operations (INCR, CAS, SETNX)
Batch reads and writes (MGET / MSET)
Scale out and rebalance without downtime
Replication and automatic failover
Non-Functional Requirements
Latency: p99 < 1 ms inside the data centre
Availability: 99.99%, replica promoted in seconds
Scalability: consistent hashing / 16,384 hash slots
Consistency: eventual across replicas, atomic per key
Efficiency: memory-optimised, no hot-key stalls
Resilience: stampede protection (locks, jittered TTL)
Durability: optional snapshots + append-only log

Cache Hit

App SDK → Proxy → CRC16(key) mod 16384 → Primary shard → value in under 1 ms

Cache Miss

Miss → app reads Origin DB → SET key with TTL on the primary shard

Failover

Heartbeat lost → Cluster Manager promotes replica → new slot map pushed to proxies

Nodes gossip heartbeats; a primary missing a quorum of heartbeats is replaced by its replica.

Eviction: allkeys-LRU / LFU. TTLs get random jitter to avoid synchronised expiry.

Scaling &amp; Failure Handling
Scale out: add a primary, migrate slots online, proxies refresh the slot map
Failure: replica promotion with epoch bump; clients retry on MOVED / ASK
Stampede: request coalescing, soft TTL, jittered expiry for hot keys
Hot key: client L1 cache plus replicated read-only copies across shards
