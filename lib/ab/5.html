Modular Monolith vs Microservices

Decide whether module boundaries are enforced inside one deployable or made physical with separate services.

THE 30-SECOND ANSWER

A modular monolith is one deployable whose modules have explicit public APIs and private data, with the boundaries verified by tooling. Microservices make those boundaries physical with separate deployments and databases. The modular monolith keeps in-process speed and simple transactions while preserving a path to extraction. Prefer it by default; extract a module when it needs independent scaling, release cadence, or isolation.

Modular Monolith vs Microservices

QUICK REVISION CARD
CORE DIFFERENCE

Enforced logical boundaries inside one deployable versus physical boundaries across separate services.

CHOOSE A WHEN

Default for most products; boundaries still evolving; cross-module transactions or low latency matter.

CHOOSE B WHEN

A module needs independent scaling, release cadence, runtime, or compliance isolation.

BIGGEST TRADE-OFF

Operational simplicity and speed versus physical isolation and independent scaling.

KEY FAILURE MODE

Boundary erosion (modular monolith); premature extraction into a distributed monolith (microservices).

ONE-LINE ANSWER

“Draw the boundaries first and enforce them; make them physical only where independence pays for the network.”
