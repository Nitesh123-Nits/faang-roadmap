Monolith vs Microservices

Decide whether the system ships as one deployable unit or as many independently deployable services.

THE 30-SECOND ANSWER

A monolith ships every capability as one deployable unit, with in-process calls and usually one database. Microservices split capabilities into independently deployable services that talk over the network. Microservices buy team and release independence at the price of distributed-systems complexity. Start with a well-structured monolith; split only when team scale, divergent scaling needs, or release coupling justify the cost.

MONOLITH
ThroughputScales by running more identical instances behind a load balancer, if the app is stateless.Scales per service, so a hot capability can get more instances without scaling the rest.
Consistencymodules.A single ACID transaction can span allNo cross-service ACID; use sagas, outbox, and eventual consistency.
AvailabilityOne bad release or memory leak can take down everything; simple failure model.Faults can be isolated with timeouts, bulkheads, and circuit breakers, but only if they are designed in; there are more failure modes.
Best use casesEarly products, small teams, unclear domain boundaries, strong transactional needs.Many autonomous teams, clearly bounded domains, parts with different scale or compliance profiles.

CHOOSE MONOLITHOne team or a few tightly coordinated teams; domain boundaries are still shifting; you need cross- entity ACID transactions; the platform and observability tooling for many services does not yet exist.
