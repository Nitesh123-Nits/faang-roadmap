THE MODEL

You declare desired state; controllers reconcile actual state toward it. Pods are disposable, Services give stable addresses, and probes plus resource settings tell Kubernetes how to treat your process.

Probes

Startup

Readiness

Liveness

  httpGet: {path: /ready, port: 8080}
  periodSeconds: 5
livenessProbe:
  httpGet: {path: /live, port: 8080}
startupProbe:
  httpGet: {path: /live, port: 8080}
  failureThreshold: 30

JAVA / SPRING

On Kubernetes

Set -XX:MaxRAMPercentage to leave headroom for nonheap memory; heap is not the whole footprint.
server.shutdown=graceful plus a terminationGracePeriodSeconds longer than your drain time.
Use Actuator liveness and readiness health groups for probes.
Keep dependencies out of liveness. A database outage should not restart every pod.
Use a startupProbe for slow JVM starts instead of long liveness delays.
Rolling deploys: readiness must reflect real ability to serve.

PRODUCTION

Readiness checklist

At least 2 replicas, spread across nodes and zones

Readiness, liveness and startup probes set

Requests and limits set; JVM sized to match

PodDisruptionBudget defined

HPA with sensible min and max

Graceful shutdown tested

Runs as non-root; read-only root filesystem

NetworkPolicy in place

Config in ConfigMap; secrets from a store

Pinned image tags or digests

ResourceQuota and LimitRange per namespace

Metrics, logs, traces and alerts wired

PITFALLS

Common mistakes

No resource requests, so HPA and scheduling mislead.
Using the latest tag.
Liveness probe that checks dependencies.
Aggressive probe timings that restart healthy pods.
Single replica with no PDB; node drains cause outages.
Treating base64 as encryption.
CPU limit set too low, causing silent throttling.
Skipping rollout status checks in pipelines.
