Service Communication Decisions

How services should talk: sync or async, which protocol, which broker, how to keep calls safe, and how to change contracts without breaking anyone.

INSIDE

Sync or async decision flow REST, gRPC, GraphQL, queues, logs

Saga, outbox, idempotency keys Timeouts, retries, breakers, contracts

DECISION FLOW

Sync or async first

Does the caller need the answer now?

↓

YES → Synchronous REST for public and partners · gRPC for hot internal paths · GraphQL for flexible client queries

↓

NO → Asynchronous Queue for work · event log for facts · saga for long workflows

DEFAULT

Default: REST between teams and to the outside, gRPC for hot internal paths, events to tell other domains what happened. Keep the sync call chain shallow.

Pick a protocol

SYNCHRONOUS

REST, gRPC, GraphQL and friends

REST / JSONPublic and partner APIs, CRUD, broad tooling. Avoid for high-volume internal calls and streaming.
gRPCInternal, low latency, strong contracts, streaming. Avoid for browsers without a proxy and ad hoc debugging.
GraphQLMany clients need different shapes. Avoid for simple CRUD; watch N+1 and query cost.
WebSocketTwo-way, low latency (chat, trading). Stateful: needs sticky routing and a scaling plan.
SSEServer-to-client stream over HTTP. Simple, auto-reconnect.
WebhookNotify an external system. Needs signatures, retries, idempotency.
ASYNCHRONOUS

Queue, log or pub/sub

Queue

RabbitMQ, SQS. One consumer per message, ack and delete, work distribution, flexible routing.

Log

Kafka. Retained and replayable, ordering per partition, many independent consumers.

Pub/sub

SNS, Redis pub/sub. Fan-out, fire and forget; check the durability guarantee.

Messages and workflows

MESSAGES

Command, event, query

Command

Do this. One receiver, may be rejected. Imperative name: ReserveStock .

Event

This happened. Immutable, many listeners. Past tense: OrderPlaced .

Query

Give me data. Synchronous, no side effects.

Event notification: small, consumers call back for details. Low coupling, more calls.
Event-carried state: the event holds the data. Consumers stay autonomous, schema coupling grows.
WORKFLOWS

Orchestration vs choreography

Orchestration

A central coordinator tells each step. Visible flow, easy to change; the coordinator is a coupling point.

Choreography

Services react to events. Loose coupling, hard to see the whole flow.

A distributed transaction is a saga: local transactions plus compensating actions. Avoid 2PC across services in most systems.

EXAMPLE

Saga: place an order

1 · Create order status PENDING

↓

2 · Reserve stock compensation: release stock

↓

3 · Charge payment compensation: refund

↓

4 · Confirm order status CONFIRMED

If step 3 fails, run compensations in reverse order and mark the order FAILED.
Every step and compensation must be idempotent and retryable.
Persist saga state so a crash can resume.
DELIVERY

Guarantees and idempotency

Networks give at-least-once: design every handler to be idempotent.
Idempotency key per request, or dedupe on a business key.
Transactional outbox: write state and event in one DB transaction, relay to the broker.
Order matters only per key: partition by that key.
Poison messages: bounded retries, then a dead-letter queue and an alert.
PATTERN

Idempotency key flow

Client sends Idempotency-Key: uuid with the write.
Server stores key, request hash and result in one transaction.
A repeat with the same key returns the stored result.
Same key with a different body is rejected (409/422).
Keys expire after a retention window.
PATTERN

Transactional outbox

In one DB transaction: update the entity and insert an outbox row.
A relay (poller or CDC) reads new rows and publishes to the broker.
Mark rows sent, or delete them, after publish.
Consumers dedupe, because the relay is at-least-once.

This closes the gap between “saved to DB” and “event published”.

Make every call safe

RESILIENCE

Every remote call needs

TimeoutAlways set. The caller's deadline is shorter than its own caller's.
RetryIdempotent calls only, exponential backoff with jitter, bounded.
Circuit breakerStop calling a failing dependency, fail fast, probe to recover.
BulkheadSeparate pools per dependency so one cannot starve the rest.
FallbackCached or degraded answer, when acceptable.
RETRY AMPLIFICATION

3 layers each retrying 3 times means up to 27 calls on the failing service. Retry at one layer and propagate deadlines.

BUDGET

Timeout budget example

client            2000 ms
  gateway         1800 ms
    service A     1500 ms
      service B   1000 ms
        database   500 ms

Each hop gets less time than its caller. gRPC propagates deadlines natively; for HTTP, pass a deadline header.

CONFIG

Resilience4j starter config

resilience4j:
  circuitbreaker.instances.payments:
    slidingWindowSize: 20
    failureRateThreshold: 50
    waitDurationInOpenState: 30s
  retry.instances.payments:
    maxAttempts: 3
    waitDuration: 200ms
    enableExponentialBackoff: true

Tune to measured behaviour. Add jitter and a retry budget where supported.

Contracts and API design

EVOLUTION

Change without breaking

Safe: add optional fields. Unsafe: remove, rename, retype, change meaning.
Consumers ignore unknown fields (tolerant reader).
Version only for breaking changes (path /v2 or a header). Run both versions during migration.
Contract tests (Pact, Spring Cloud Contract) catch breaks in CI.
Messages: schema registry with backward or full compatibility.
G R P C

What to know

Four call types: unary, server stream, client stream, bidirectional.
Always set a deadline; it propagates down the call chain.
Protobuf: never reuse or renumber a field; add new fields only.
Long-lived HTTP/2 connections: use client-side or L7 load balancing.
API DESIGN

Checklist for a good HTTP API

Cursor pagination on lists

Consistent error body (RFC 9457 problem details)

429 with Retry-After for rate limits

Idempotency keys on unsafe writes

Versioning and deprecation policy

Timeouts documented and enforced

Authentication on every route

OpenAPI spec kept in CI

NETWORK

Discovery, load balancing, security

Kubernetes Service DNS covers most discovery; a mesh adds mTLS, retries and traffic shifting.
gRPC keeps long-lived HTTP/2 connections: an L4 load balancer pins them to one pod. Use client-side or L7 balancing.
Authenticate services: mTLS or OAuth2 client credentials. Propagate the user's identity token only when needed.
Gateway for north-south traffic, mesh or direct calls for east-west.
SMELLS

Common mistakes

Distributed monolith: services deploy together or share a database.
Chatty calls and deep sync chains: latency multiplies, availability multiplies down.
No timeouts or unbounded retries.
Events that are really commands in disguise.
Breaking a contract without a version or contract test.

Choose the weakest coupling that meets the requirement. Ask whether the caller must wait; if not, publish an event. Always set timeouts and make handlers idempotent.
