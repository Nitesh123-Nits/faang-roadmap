THE ORDER

A fast, boring rollback beats a clever diagnosis while users are down.

First ten minutes

FIRST 10 MINUTES

Order of operations

Acknowledge and assign roles: incident commander, ops lead, communications.
Set severity using your organisation's definitions.
Confirm impact: who, what, since when. Check the latest deploy and config changes.
Mitigate before you find the root cause.
Post the first status update. Start a timeline.
Capture evidence before restarting anything.
FIRST 10 MINUTES

Mitigation toolbox

Roll backFastest fix when a recent deploy correlates
Flag offDisable the new feature or path
Scale outBuys time when saturated; may move the bottleneck
Shed loadRate limit, drop non-critical traffic
Fail overTo replica, standby or another zone
Circuit breakCut a failing dependency; serve degraded
RestartLast resort. Take thread and heap dumps first
COMMUNICATE

Status update template

Impact: what users see, and how many.
Status: investigating, mitigating or monitoring.
What we know: facts only.
Next update: a specific time.
Update on a fixed cadence, even with no news.
Separate facts from hypotheses.
One person owns external communication.

INVESTIGATE

Questions that find the cause

What changed? Deploy, config, flag, data, traffic, dependency.
When exactly did it start? Match to the timeline.
Who is affected? All users, one region, one tenant, one endpoint.
Which signal moved first: latency, errors, saturation?
Does it reproduce in staging or on one host?
What does the dependency's own dashboard show?

Commands

J A V A

JVM triage

# hottest threads
top -H -p <pid>
printf '%x\n' <tid>   # = nid in dump
jcmd <pid> Thread.print > t.txt

# memory and GC
jstat -gcutil <pid> 1000
jcmd <pid> GC.heap_info
jmap -histo:live <pid> | head -30
jcmd <pid> GC.heap_dump /tmp/h.hprof

# profiling
jcmd <pid> JFR.start duration=60s \
  filename=/tmp/r.jfr
Take two or three thread dumps a few seconds apart; one proves little.
Enable HeapDumpOnOutOfMemoryError in production JVMs.
H O S T

Linux triage

top            # CPU, load
vmstat 1       # run queue
iostat -x 1    # disk
free -m        # memory
df -h; df -i   # space
ss -s          # sockets
dmesg -T | tail   # OOM kill
journalctl -u svc -n 200

Use the USE method: utilisation, saturation and errors for each resource.

DATABASE

Database triage

MySQL: SHOW FULL PROCESSLIST , SHOW ENGINE INNODB STATUS , slow query log.
PostgreSQL: pg_stat_activity , pg_locks , pg_stat_statements .
Look for long transactions, lock waits and a single query dominating load.
Check connection count against the pool and the server limit.
Check replication lag before reading from replicas.
Do not kill sessions without knowing what they are.
TOOLS

Little's Law and saturation

In flight = rate × latency. A rise in latency raises concurrency and can exhaust pools.
Saturated resources grow queues; queues grow latency non-linearly.
Retries multiply load. A retry storm can keep a recovering system down.
Find the first saturated resource, fix it, then measure again.
The bottleneck moves after each fix.

Patterns and learning

PATTERNS

Failure patterns to recognise

Retry stormClients retry a struggling service. Add backoff, jitter and retry budgets
Thundering herdMany callers wake at once. Stagger, jitter, queue
Cache stampedeHot key expires, all miss. Lock, early refresh, stale-while-revalidate
Cascading failureOne slow dependency exhausts callers' threads. Timeouts, bulkheads, breakers
Noisy neighbourShared resource contention. Isolate or limit
Slow leakMemory or connections grow until failure. Trend dashboards
PITFALLS

Mistakes that extend outages

Changing several things at once, so you cannot tell what worked.
Restarting before capturing evidence.
Silence: no updates for long stretches.
Chasing root cause while users are still impacted.
Blaming people instead of finding system gaps.
Declaring resolved without monitoring recovery.
AFTER

Blameless postmortem outline

Summary, impact and duration.
Timeline of detection, decisions and actions.
Root cause and contributing factors (ask why repeatedly).
What went well, what went badly, where we got lucky.
Action items with owners and dates, prioritised.

Detection gap: how could we have known sooner?
