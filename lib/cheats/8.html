Kafka in one picture

Producers key → partition

↓

Topic: orders (3 partitions, RF = 3) P0 · P1 · P2, each an ordered append-only log

↓

Consumer group: payments one partition → one consumer in the group

↓

Offsets committed per partition lag = log-end offset − committed offset

THE RULE

Kafka is a distributed log. Ordering lives in a partition, parallelism is the partition count, durability comes from replication, and delivery guarantees come from when you commit.

Concepts

MODEL

Core concepts

PartitionOrdered, append-only log; unit of parallelism and ordering
OffsetPosition of a record within a partition
BrokerServer storing partitions
Replica / ISRLeader plus followers; ISR = in-sync replicas
Consumer groupMembers split a topic's partitions; each partition goes to one member

MODEL

Ordering and partitioning

Order is guaranteed only within a partition.
The record key picks the partition, so one key keeps its order.
Maximum consumer parallelism in a group = partition count.
Adding partitions changes the key → partition mapping for new records.
A skewed key creates a hot partition. Pick the key for ordering needs first, then check the distribution.

Guarantees

GUARANTEES

Delivery semantics

At most onceCommit offset, then process. Can lose messages
At least onceProcess, then commit. Can duplicate. The usual default
Exactly onceIdempotent producer + transactions + read_committed, inside Kafka. Outside Kafka, make the sink idempotent
ALWAYS

Design consumers to be idempotent regardless.

GUARANTEES

Durability recipe

replication.factor=3
min.insync.replicas=2
acks=all
enable.idempotence=true
unclean.leader.election.enable=false
With acks=all , a write succeeds only if at least min.insync.replicas replicas have it.
Idempotence is on by default in recent clients; make it explicit.
One broker can fail with no loss and no write outage.

Operations

OPERATIONS

Rebalances and lag

Triggers: member joins or leaves, session timeout, poll interval exceeded, partition change.
Use the cooperative sticky assignor to avoid stop-theworld rebalances.
Use static membership for rolling restarts.
Keep per-poll processing well under max.poll.interval.ms .
Lag rising means consumers are slower than producers, or are stuck in rebalance loops.
Scale consumers only up to the partition count.
PATTERNS

Reliability patterns

Transactional outbox for DB write + publish atomically.
Idempotent consumer: dedupe on a business key.
Retry topics with delays, then a dead-letter topic.
Handle poison messages: tolerant deserializers, DLQ, alert.
Backpressure with pause and resume.
Spring Kafka: DefaultErrorHandler with backoff, DeadLetterPublishingRecoverer , @RetryableTopic .
STORAGE

Retention and compaction

delete policyDrop old segments by retention.ms or retention.bytes
compact policyKeep the latest record per key; null value = tombstone
segment.bytesSegment size; affects cleanup granularity
Disk estimatethroughput × retention × replication factor

Tiered storage depends on your Kafka version and vendor; check before relying on it.

D ATA

Schemas and compatibility

Use a schema registry with Avro, Protobuf or JSON Schema.
Modes: BACKWARD, FORWARD, FULL (plus transitive variants).
Add optional fields with defaults. Never reuse a field number or change a type.
Version event names and keep consumers tolerant of unknown fields.

Commands

# BS = --bootstrap-server h:9092
kafka-topics.sh $BS --create \
  --topic t --partitions 6 \
  --replication-factor 3

kafka-topics.sh $BS \
  --describe --topic t

kafka-console-consumer.sh $BS \
  --topic t --from-beginning

kafka-consumer-groups.sh $BS \
  --describe --group g

kafka-consumer-groups.sh $BS \
  --group g --topic t \
  --reset-offsets --to-earliest \
  --execute

Resetting offsets needs the group to be inactive. Run without --execute first to preview.

SIZING

Partitions and capacity

Partitions ≈ target throughput ÷ measured per-partition throughput, on the producer and consumer side. Take the larger.
More partitions mean more open files, slower recovery and longer rebalances.
Plan for future consumer parallelism; you cannot reduce partitions.
Use RF 3 across zones for production topics.
F I T

Kafka or not

Use for

Replayable event log, many consumers, high throughput, stream processing, CDC

Avoid for

Per-message routing and priority, lowvolume task queues, request-reply

Operating Kafka is a team cost; weigh managed offerings.
