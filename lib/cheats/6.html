THE HABIT

Read the query plan, check the index, shorten the transaction, then scale. Most database incidents are one of those four.

For backend engineers working with MySQL, PostgreSQL and MongoDB.

Indexes and queries

INDEXES

Indexing rules

B-tree indexes serve equality, range and ordering on the leading columns.
Composite index: order columns by equality first, then range; the leftmost-prefix rule applies.
Covering index: the query is answered from the index alone.
Functions on the column ( LOWER(col) ) or a leading wildcard ( LIKE '%x' ) defeat a normal index.
Implicit type conversion can silently skip an index.
Every index slows writes and uses space. Drop unused ones.
Low-cardinality columns alone are poor indexes.
QUERIES

Reading a query plan

Run EXPLAIN (and EXPLAIN ANALYZE where available).
Red flags: full scan on a large table, a sort on disk, temporary tables, rows examined far above rows returned.
Stale statistics mislead the planner; refresh them ( ANALYZE ).
Fix the query and index first, hints last.
EXPLAIN ANALYZE
SELECT ... FROM orders
WHERE customer_id = ?
ORDER BY created_at DESC
LIMIT 20;

Pagination

Offset

Simple, but cost grows with depth; unstable if rows change

Keyset (seek)

Stable and fast. Needs a unique, indexed sort key.

WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT n

Return a cursor, not a page number, for large feeds.

Transactions

TRANSACTIONS

Isolation levels

Read uncommittedDirty reads possible
Read committedNo dirty reads. Non-repeatable reads and phantoms possible
Repeatable readStable reads in a transaction. Behaviour on phantoms differs by engine
SerializableAs if run one at a time. Most conflicts and retries
Common defaults: MySQL InnoDB uses repeatable read; PostgreSQL uses read committed.
Snapshot-style repeatable read can still allow write skew.
Higher isolation costs throughput; handle serialization failures with retries.
TRANSACTIONS

Locking and concurrency

Optimistic: a version column and a conditional update. Best with low contention.
Pessimistic: SELECT … FOR UPDATE . Best when conflicts are frequent.
SKIP LOCKED lets workers claim rows without blocking (PostgreSQL and MySQL 8).
Avoid deadlocks: lock in a consistent order and keep transactions short.
Never hold a transaction open across a remote call.
Make writes idempotent so retries are safe.
O R M

N+1 and ORM pitfalls

Symptom: one query for the list, then one per row.
Fix: fetch join, @EntityGraph , batch fetching, or a DTO projection.
Lazy loading outside a transaction throws LazyInitializationException .
Avoid returning entities from APIs; return DTOs.
Set ddl-auto to none or validate in production; use Flyway or Liquibase.
Log SQL and count statements in tests for hot paths.

Design and scale

DESIGN

Schema design

Normalise by default; denormalise deliberately for proven read paths.
Money: DECIMAL or integer minor units, never floating point.
Store timestamps in UTC.
Random UUIDs fragment B-tree indexes; time-ordered IDs (UUIDv7, ULID, snowflake) insert more smoothly.
Soft deletes complicate uniqueness and queries; weigh the cost.
Add foreign-key indexes where you join or delete.
SCALE

Scaling ladder

Fix queries and indexes
Tune connection pooling
Cache hot reads
Read replicas (mind replication lag)
Archive or partition large tables
Shard by a well-chosen key

Replica reads can be stale; route read-your-writes traffic to the primary.

SCALE

Connection pools

The pool should be small and sized by measurement. HikariCP's pool-sizing guidance explains why far fewer connections often perform better.
Total connections across all instances must fit the server's limit.
Watch pool wait time as an early warning.
CONSISTENCY

Replication and consistency

Async replicationFast writes; replicas can lag; failover can lose recent writes
Sync replicationNo loss on failover; higher write latency
Read-your-writesRoute a user's reads to the primary shortly after a write
FailoverAutomate, fence the old primary, test regularly
CACHING

Caching with a database

Cache-aside is the default: read, miss, load, store.
Set TTLs; decide how invalidation happens on writes.
Protect hot keys from stampedes with locking or early refresh.
Cache the result of expensive queries, not everything.
The database remains the source of truth.
PARTITIONING

Partitioning vs sharding

PartitioningSplit a table inside one database: prune scans, drop old data cheaply
ShardingSplit data across servers: scales writes and storage, adds complexity
Shard keyHigh cardinality, even load, matches common queries

Cross-shard joins and transactions are the cost.

SQL, change and documents

S Q L

Features worth knowing

CTEs and window functions ( ROW_NUMBER , LAG , running totals).
JOIN types, and when an anti-join ( NOT EXISTS ) is clearer than NOT IN .
Upsert: INSERT … ON CONFLICT (PostgreSQL) or ON DUPLICATE KEY UPDATE (MySQL).
Partial and functional indexes where supported.
JSON columns for flexible attributes; index the fields you filter on.
Bulk operations and batching instead of row-by-row loops.
CHANGE

Safe migrations

Expand, migrate, contract: add, backfill in small batches, switch, then drop.
Check how your engine's DDL locks the table before running it on production.
Keep schema and code deployable in either order.
Test rollbacks and keep backups current.
MONGODB

Document-store essentials

Model by access pattern: embed data read together; reference when it grows without bound or is shared.
Compound index order: Equality, Sort, Range.
Shard key needs high cardinality and even distribution; avoid monotonically increasing keys.
Choose read and write concerns to match durability needs.
Documents have a size limit; avoid unbounded arrays.
OPERATIONS

Backup and recovery

Define RPO and RTO first.
Point-in-time recovery needs continuous log archiving.
A backup you have not restored is a hope, not a backup.
Test restores on a schedule.
PITFALLS

Common mistakes

SELECT * on wide tables.
Missing index on a foreign key or a filter column.
OR conditions and huge IN lists that skip indexes.
COUNT(*) on very large tables on a hot path.
Long transactions and idle-in-transaction sessions.
Treating the cache as the source of truth.
Running migrations that lock a busy table.
THE RULE

Measure before tuning: read the plan, check the index, shorten the transaction, then scale.
