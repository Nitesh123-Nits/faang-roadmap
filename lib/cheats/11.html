Concepts

CONCEPTS

Signals and questions

MetricsIs something wrong, and how bad? Cheap numbers over time. Alerts and trends.
LogsWhat exactly happened? Events with context. Expensive at volume.
TracesWhere did the time go across services? One request, many spans.
ProfilesWhich code burns CPU or memory? Continuous profiling.
EventsWhat changed? Deploys, flags, config. Overlay on dashboards.
METHOD

Golden signals, RED, USE

Golden signals

Latency, traffic, errors, saturation. Every service.

RED

Rate, Errors, Duration. For request-driven services.

USE

Utilization, Saturation, Errors. For resources: CPU, pool, disk, queue.

Start with RED per endpoint and USE per resource (JVM heap, Hikari pool, thread pool, Kafka lag).

RELIABILITY

SLI, SLO, error budget

SLI: good events ÷ valid events (e.g. requests under 300 ms that are not 5xx).
SLO: target for the SLI over a window (99.9% over 30 days).
Error budget = 1 − SLO. 99.9% allows about 43 minutes of bad time per 30 days.
Budget burning fast: freeze risky releases, fix reliability first.

Alerting

ALERTING

Alert on symptoms and burn rate

Page on user pain (errors, latency, SLO burn), not on causes (CPU 80%).
Every page is urgent, actionable and links a runbook.
Multi-window burn rate (30-day SLO): page at 14.4× over 1 h and 5 min; page at 6× over 6 h; ticket at 1× over 3 days.
Route by severity: page, ticket, or dashboard only.
Delete alerts nobody acts on.
T E S T

If an alert fires and the response is “wait and see”, it is not a page.

ALERTING

Prometheus alert rule example

- alert: HighErrorRatio
  expr: |
    sum(rate(
      http_server_requests_seconds_count
        {status=~"5.."}[5m]))
    / sum(rate(
      http_server_requests_seconds_count
        [5m])) > 0.02
  for: 5m
  labels: {severity: page}
  annotations:
    runbook_url: https://runbooks/x

Prefer SLO burn-rate rules for paging; use simple thresholds for tickets.

Metrics, logs, traces

METRICS

Types and cardinality

Counter

Only goes up. Use rate(). Requests, errors.

Gauge

Goes up and down. Queue size, heap.

Histogram

Buckets, aggregatable across instances. Use for latency.

Summary

Client-side quantiles, cannot be aggregated.

Never average percentiles. Aggregate histogram buckets, then compute the quantile.
Labels multiply series. No user IDs, request IDs or raw URLs as labels.
METRICS

Business metrics with Micrometer

Counter.builder("orders.placed")
    .tag("channel", "web")
    .register(registry)
    .increment();

Timer t = Timer.builder("payment.latency")
    .publishPercentileHistogram()
    .register(registry);
t.record(() -> charge(order));

Count things the business cares about, not only HTTP.

L O G S

Structured logging

JSON, one event per line, fixed field names.
Always include traceId , spanId , service, version, level.
Log decisions and failures, not every step. No PII, tokens or secrets.
Log once at the boundary where the error is handled, not at every layer.
Sample or drop DEBUG in production.
Spring Boot 3.4+: logging.structured.format.console=ecs .
L O G S

Log levels

ERROR

Needs a human or a fix. Should be rare and actionable.

WARN

Unexpected but handled. Watch the trend.

INFO

Business events and lifecycle. Default in production.

DEBUG

Developer detail. Off in production, switchable at runtime.

TRACING

Context propagation and sampling

traceparent:
 00-4bf92f3577b34da6a3ce929d0e0e4736
 -00f067aa0ba902b7-01
 ver · trace id (32 hex) · span id (16 hex) · flags
W3C traceparent is the standard header. Propagate it through HTTP and Kafka/AMQP headers.
Head sampling: decide at start, cheap, may miss rare errors.
Tail sampling: decide after the trace ends (keep errors and slow ones). Runs in the collector.
Async hops and thread pools lose context unless wrapped.
ASYNC

Tracing Kafka and async work

Propagate trace context in message headers.
Spring Kafka (Boot 3.2+): enable spring.kafka.template.observation-enabled and spring.kafka.listener.observation-enabled .
Link consumer spans to the producer span so a trace crosses the broker.
Wrap custom executors so context follows the thread.

Run it

TRIAGE

Alert to root cause

Open the RED dashboard for the service.
Check what changed: deploy, flag, config.
Follow an exemplar or slow trace to the failing span.
Open logs by traceId .
Confirm resource saturation: pool, GC, lag.
Mitigate first (roll back, scale, shed load), then fix.
SPRING

Spring Boot setup

// build.gradle dependencies
spring-boot-starter-actuator
micrometer-registry-prometheus
micrometer-tracing-bridge-otel

# application.yml
management:
  endpoints.web.exposure.include:
    health,prometheus
  endpoint.health.probes.enabled: true
  tracing.sampling.probability: 0.1
  metrics.distribution:
    percentiles-histogram:
      http.server.requests: true

Keep sampling low in production; use tail sampling if you need all errors.

COLLECTOR

OpenTelemetry Collector shape

receivers:
  otlp: {protocols: {grpc: {}, http: {}}}
processors:
  memory_limiter: {check_interval: 1s,
                   limit_percentage: 80}
  batch: {}
exporters:
  # one per backend
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [<tempo>]
    metrics: {...}  # → Prometheus
    logs: {...}     # → Loki

Exporter names depend on your backends; check the docs for your versions.

DASHBOARDS

Design a dashboard people use

Top row: SLO and RED for the service.
Second row: dependencies (DB, cache, downstream calls).
Third row: resources (JVM, pool, CPU, memory).
Annotate deploys and flag changes.
Link panels to traces and logs.
One purpose per dashboard; about a dozen panels at most.
C O S T

Anti-patterns and cost control

Dashboards with 40 panels nobody reads: keep one RED page per service.
Alerting on every error log line.
High-cardinality labels: the fastest way to break Prometheus and the bill.
Logging full request bodies: cost and privacy risk.
Keeping everything at full resolution: set retention tiers, drop DEBUG, sample traces, downsample old metrics.
No ownership: every dashboard and alert has a team.

Monitoring tells you something is broken; observability lets you ask why. Alert on SLO burn, correlate by traceId, and keep cardinality and cost under control.
