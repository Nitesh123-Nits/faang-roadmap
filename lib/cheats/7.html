Where and how

LAYERS

Where to cache

Browser / HTTPStatic assets, GET responses with Cache- Control. Free, zero network.
CDNPublic, shared content close to users. Offloads origin.
In-process (L1)Caffeine. Fastest, but per instance: copies diverge, no shared invalidation.
Distributed (L2)Redis or Memcached. Shared across instances, network hop, own failure modes.
DatabaseBuffer pool, query plans, read replicas. Tune before adding another layer.
PATTERNS

Caching strategies

Cache-asideApp reads cache, on miss loads DB and fills. Default choice. Risk: stale data, stampede.
Read-throughCache loads from DB itself. Simpler app code, needs a loader.
Write-throughWrite cache and DB together. Fresh reads, slower writes.
Write-behindWrite cache, flush to DB later. Fast writes, can lose data on crash.
Write-aroundWrite DB only, cache fills on read. Good for write-once, rarely-read data.
Refresh-aheadReload hot keys before expiry. Smooth latency, wasted work on cold keys.
DESIGN

Cache key design

Pattern: service:entity:id:v3 . Include tenant, locale and version when they change the value.
Keep keys short and readable; hash long query strings.
Never put secrets or raw PII in keys.
Namespace by environment so test and prod never collide.
Cache DTOs, not JPA entities. Make values immutable and serialisable.
Version the value schema so a deploy does not read old shapes.

Freshness

FRESHNESS

Invalidation

TTL is the safety net. Always set one, and add random jitter (±10–20%).
Delete on write, do not update: the next read refills. Updating the cache from a write path invites race conditions.
Event-driven: publish change events (outbox, CDC) and evict in every consumer. Best for multi-service caches.
Versioned keys ( product:42:v7 ): never invalidate, old keys expire.
Tag or prefix groups for bulk eviction, via a set of keys per tag.
Know your staleness budget per data type: price and stock differ from a profile photo.
THE RACE TO KNOW

Reader misses and loads the old row, writer updates the DB and deletes the key, reader then writes the old value into the cache. Fix with short TTL, versioned keys, or a delayed second delete.

FAILURE MODES

Symptom → cause → fix

StampedeHot key expires, many requests hit the DB. Single-flight lock, early probabilistic refresh, stale-while-revalidate.
PenetrationRequests for keys that never exist. Cache the negative result with a short TTL, or use a Bloom filter.
AvalancheMany keys expire together. TTL jitter, staggered warm-up.
Hot keyOne key saturates a shard. Put L1 in front, or replicate the key with suffixes k#1..k#N .
Big keyA large value blocks the single-threaded server. Split, compress, use hash fields.
Cache downDB overload. Circuit breaker, bulkhead, load shedding, degrade gracefully.
Cold startAfter deploy or failover. Pre-warm hot keys, ramp traffic.

Memory and Redis

MEMORY

Eviction policies

LRUDrops the least recently used. Good default.
LFUDrops the least frequently used. Resists one-off scans.
TTLExpires by time. Always combine with a size limit.
CaffeineWindow TinyLFU: near-optimal hit rate, bounded size.
maxmemory 2gb maxmemory-policy allkeys-lru
# allkeys-lfu · volatile-lru
# volatile-ttl · noeviction (default)

With noeviction, writes fail when memory is full. Cache workloads normally want allkeys-lru or allkeys-lfu.

REDIS

Pick the data structure

StringValues, counters (INCR), locks (SET NX EX).
HashObject fields, partial updates.
ListQueues, recent items.
Set / ZSetTags and uniqueness. ZSet: leaderboards, rate-limit windows, delayed jobs.
StreamLog with consumer groups. Use Kafka when durability and scale matter.
Bitmap / HLLFlags per user, approximate unique counts.
REDIS

Deployment topologies

StandaloneDev and small caches. Single point of failure.
SentinelPrimary plus replicas with automatic failover. One shard only.
Cluster16384 hash slots sharded across nodes. Multi-key commands need the same slot (hash tags like {user42} ).
PersistenceRDB and AOF are optional. Replication is async: a failover can lose recent writes.
REDIS

Sizing a cache

Estimate: items × (average value size + per-key overhead) × replication factor.
Leave headroom for fragmentation, replication buffers and fork copy-on-write; do not run maxmemory at 100% of RAM.
Hit ratio depends on skew: a small hot set gives a high ratio from a small cache.
Measure hit ratio at two cache sizes before buying more memory.

Patterns with Redis

PATTERN

Distributed lock: know the limits

SET lock:order:42 token NX PX 30000
# release only if the token matches
# (use a Lua script: GET, compare, DEL)
The lease can expire during a long GC pause or slow call while you still think you hold the lock.
For correctness, use a fencing token checked by the resource, or a database constraint.
Use Redis locks for efficiency (avoid duplicate work), not as the only safety net.
PATTERN

Rate limiting with Redis

Fixed window

INCR a key per window, EXPIRE. Simple; allows bursts at the boundary.

Sliding window

ZSET of timestamps, trim then count. Accurate, more memory.

Token bucket

Refill rate plus capacity, via a Lua script. Smooth, burst-friendly.

Make the check-and-update atomic with a Lua script or a single command; two round trips race.

EXAMPLE

Worked example: product catalogue

Read-heavy, tolerates a little staleness: cache-aside.
L1 Caffeine, 30 s TTL, plus L2 Redis, 10 min TTL with jitter.
Price change event (outbox, Kafka) evicts the key in both layers.
Stock level: not cached, or a very short TTL, because correctness matters.
Single-flight loading on miss to stop stampedes on popular items.
Dashboards: hit ratio, p99 with and without cache, eviction rate.

In Spring and HTTP

SPRING

Spring Boot caching

@EnableCaching

@Cacheable(cacheNames = "products",
           key = "#id", sync = true)
Product get(long id) { ... }

@CacheEvict(cacheNames = "products",
            key = "#p.id")
void update(Product p) { ... }

# application.yml
spring.cache.type: caffeine
spring.cache.caffeine.spec: >
  maximumSize=10000,
  expireAfterWrite=10m
Annotations work through proxies: self-invocation and private methods bypass the cache.
sync=true stops a stampede only within one JVM.
Redis: set spring.cache.redis.time-to-live or configure RedisCacheManager with per-cache TTL.

WHEN NOT TO CACHE

Do not cache when data changes on every read, the hit rate stays low, or correctness needs strong consistency.

THE RULE

A cache is a copy, and every copy can be wrong. Decide the staleness you accept, set a TTL, protect the database from stampedes, and measure the hit ratio before and after.
