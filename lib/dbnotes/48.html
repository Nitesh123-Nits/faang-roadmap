Database Optimization

Build fast, scalable and cost-effective data systems.

WHY OPTIMISE

Faster queries, better resource use, lower latency, higher throughput, lower cost, scalability and reliability. Track key metrics: latency (p95/p99), QPS/TPS, throughput, CPU/ memory/IOPS, cache hit ratio, lock wait time, slow-query count.

SYSTEM DESIGN VIEW
Clients -> Load balancer -> App servers
                              --> Cache layer (Redis / Memcached)
                              --> Database cluster
                                     Primary (writes)
                                     Replicas (reads)
                              --> Object storage (S3 / GCS)
Monitoring and observability: metrics, logs, alerts

Reads fan out to replicas and cache; writes go to the primary.

SCHEMA AND MODELING BEST PRACTICES
Use appropriate data types (the smallest that fits).
Normalise when it helps, denormalise for performance when measured.
Choose the right keys (primary, composite, surrogate).
Avoid nullable columns in large tables.
Use consistent naming conventions.
INDEXING STRATEGIES
Index columns used in WHERE , JOIN , ORDER BY , GROUP BY .
Use composite indexes for multi-column filters.
High cardinality before low cardinality in the key order.
Avoid over-indexing, since indexes slow writes.
Regularly review unused indexes.
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);       -- composite
CREATE INDEX idx_orders_cover ON orders(status, created_at, amount);    -- covering
-- Avoid: low-selectivity index
CREATE INDEX idx_gender ON users(gender);
