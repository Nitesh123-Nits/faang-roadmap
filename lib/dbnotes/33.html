Example: Transaction A runs SELECT * FROM account WHERE id = 1 FOR UPDATE , the row is locked, it updates the balance and commits, and the lock is released. Transaction B issues the same statement, waits, then acquires the lock and proceeds.

IN SPRING DATA JPA

Optimistic: add a version field.

@Entity
public class Account {
    @Id
    private Long id;
    private Double balance;
    @Version
    private Long version;
}
-/ Generated: UPDATE --. WHERE id = ? AND version = ?
-/ On mismatch: OptimisticLockException (Spring wraps it as
ObjectOptimisticLockingFailureException)

Pessimistic: lock on read.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Account findByIdForUpdate(@Param("id") Long id);
-/ Generated: SELECT * FROM account WHERE id = ? FOR UPDATE

OPTIMISTIC WHENPESSIMISTIC WHEN

THE 30-SECOND INTERVIEW ANSWER

Optimistic locking assumes conflicts are rare and uses a version field to detect concurrent updates at commit time. It scales better because no lock is held. Pessimistic locking assumes conflicts are common and locks the data with SELECT FOR UPDATE , preventing other transactions from modifying it until the transaction completes. Use optimistic for read-heavy systems, and pessimistic when data consistency is critical and write contention is high.

QUICK MEMORY TRICK

Optimistic: "Trust first, verify later." Pessimistic: "Lock first, then work."
