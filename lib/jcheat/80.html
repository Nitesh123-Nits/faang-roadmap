Reference Design 6 — Ride Booking

Drivers

GPS every 4 s

Riders

Offer ride to one driver at a time with timeout (driver lock with TTL) →avoid double assignment. Shard geo index by city/region.

Ride booking. High‐frequency location writes go to an in‐memory geo index; trips are durable state machines.

AspectDesign notes
Key APIsPUT /drivers/{id}/location (stream) · POST /rides {pickup, dropoff} · POST /rides/{id}/accept · WebSocket updates
Data modelephemeral: driver location + status in geo index (geohash/H3 cell →drivers); durable: trips(id, rider, driver, state, fare, timestamps)
Flowrider requests →matching queries nearby available drivers →offer to best driver with TTL lock →accept →trip state machine REQUESTED→ACCEPTED→ARRIVED→IN_PROGRESS→COMPLETED
Bottleneckslocation write rate (drivers × 1/4 s) →in‐memory, sharded by region; don't write each ping to SQL
Failure modesdriver accepts two rides →atomic driver status transition; phone offline →timeouts & reassignment
Trade‐offsmatching quality (global optimisation) vs latency (greedy nearest)

Push (fan-out on write) for normal users; pull (fan-out on read) for accounts with millions of followers.

Celebrity posts

pull at read

News feed. Precompute feeds for most users; merge celebrity posts at read time.

AspectDesign notes
Key APIsPOST /posts · GET /feed?cursor=… · POST /follow/{id}
Data model; follow graph ; feed cache: ZSET posts(id, author_id, created_at, …) (follower, followee) feed:{user} of post ids scored by time/rank
Flowwrite: store post →event →fan‐out workers push id into followers' feeds (skip inactive users). Read: get ids from feed cache, merge pulled celebrity posts, hydrate posts (batch cache), rank
Bottlenecksfan‐out to millions of followers (celebrity problem) →pull model for them; hydration N+1 →multi‐get
Failure modesfan‐out lag →feed slightly stale (acceptable); cache loss →rebuild from graph + posts
Trade‐offspush = fast reads, expensive writes; pull = cheap writes, slow reads; hybrid = complexity
