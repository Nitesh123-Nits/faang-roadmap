AspectDesign notes
Key APIsGET /shows/{id}/seats · POST /holds {showId, seatIds} →holdId, expiresAt · POST /bookings {holdId, paymentToken}
Data modelseats(show_id, seat_id, status AVAILABLE/HELD/BOOKED, hold_id, hold_expires_at, version) , PK (show_id, seat_id) ; bookings , payments
Invariantno double booking →enforced by DB conditional update / unique constraint, not by cache
Flowhold (conditional UPDATE where AVAILABLE, or Redis SET NX per seat + DB) →pay with idempotency key → confirm (UPDATE where HELD and hold matches) →release on expiry/failure
Bottlenecksflash sales: 100× traffic on one show →virtual waiting room, rate limits, cache seat map (stale OK for display)

11.10Reference Design 5 — Distributed Job Scheduler

Distributed job scheduler

Job API

create/cancel

Claim: UPDATE jobs SET lease_until = now() + interval '60 s', owner = :me
WHERE id IN (SELECT id FROM jobs WHERE next_run_at <= now() AND (lease_until IS NULL OR lease_until < now())
ORDER BY next_run_at LIMIT 100 FOR UPDATE SKIP LOCKED)
→at-least-once  execution: jobs must be idempotent; expired leases are re-claimed.

Results

history

Job scheduler. Leases + SKIP LOCKED let many schedulers claim due jobs without double execution in the normal case.

AspectDesign notes
Key APIsPOST /jobs {type, payload, schedule (cron/at), timeout, retries} · DELETE /jobs/{id} · GET /jobs/ {id}/runs
Data modeljobs(id, cron, next_run_at, status, lease_until, owner, attempts) ; job_runs(job_id, started_at, finished_at, result)
Flowschedulers poll due jobs with lease →enqueue →workers execute with heartbeat →record run →compute next_run_at
Bottleneckspolling hot index next_run_at ; thundering herd at :00 →jitter schedules
Failure modesworker dies →lease expires →re‐run (so jobs must be idempotent); clock skew →use DB now()
Scalingpartition jobs by hash(id) across scheduler shards; time‐bucketed tables / delay queues for huge volumes
Trade‐offsexactly‐once impossible →at‐least‐once + idempotency; simplicity (DB) vs throughput (dedicated queue)
