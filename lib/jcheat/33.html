4.12CQRS and Event Sourcing

CQRSEvent sourcing
Ideaseparate write model from read model(s)store events as the source of truth; state = fold(events)
Benefitsread models optimised per query; scale reads independentlyfull audit history, temporal queries, rebuild projections
Costseventual consistency between models; sync pipelineevent schema evolution forever, snapshots, complex debugging, GDPR erasure
Use whenread and write shapes/loads differ hugelyaudit is a core requirement (ledgers), domain is naturally event‐based
Combined?often with ES, but CQRS alone is far more commonalmost always needs CQRS for queries
DECISION
RULE

Start with a normal relational model + read replicas or a denormalised read table. Add CQRS projections (e.g. into Elasticsearch) per query need. Adopt event sourcing only where the event log is the business (ledger, bookings), never system‐wide by default.

4.13Eventual Consistency and Compensating Actions

State how stale is acceptable per use‐case (seconds for inventory display, never for balances).
UX patterns: "Order received — confirmation in a moment", optimistic UI, status polling, websockets.
Read‐your‐writes: route a user's reads to the primary for N seconds after a write, or return the written entity in the

response.

Reconciliation jobs are a feature, not a hack: periodically compare ledgers/systems and repair drift.

4.14Database per Service and Data Ownership

Each service is the only writer and reader of its tables. Others use its API or events.
Need another service's data for queries? Keep a local replica/projection fed by events (with only the fields you need).
Reporting across services →stream events/CDC to a warehouse, don't join across live service DBs.
Shared reference data (countries, currencies) can be a library or a read‐only feed.
