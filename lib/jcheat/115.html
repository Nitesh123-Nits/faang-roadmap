R.8 One‐Page Checklist: Distributed Systems

Correctness

Failure handling

☐Every operation that can be retried is idempotent ☐Consistency requirement written per operation ☐Invariants enforced by the database (unique keys, conditional updates), not caches ☐No wall‐clock ordering across machines ☐Locks for correctness have fencing tokens or are replaced by DB constraints ☐Dual writes eliminated (outbox / CDC) ☐Sagas have compensations, timeouts and persisted state ☐Reconciliation jobs for money and inventory

Messaging

☐Partition keys chosen for ordering and balance ☐At‐least‐once delivery + dedup window ≥replay window ☐Schema compatibility enforced in a registry ☐Poison messages routed to DLT with replay tooling

☐Timeouts budgeted end‐to‐end; deadlines propagated ☐Retry budgets; jittered backoff; single retry layer ☐Circuit breakers, bulkheads, load shedding at the edge ☐Graceful degradation plan per dependency (critical vs optional) ☐Health checks don't cascade (liveness local only) ☐Split‐brain prevention: quorums, leases, fencing

Operations

☐SLOs and error budgets defined; burn‐rate alerts ☐Tail latency (p99) tracked per hop; fan‐out minimised ☐Hot keys/partitions monitored ☐Capacity headroom for N+1 zone failure ☐Chaos / game days; RPO and RTO tested
