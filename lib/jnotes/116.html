CHAPTER 65

Pessimistic vs Optimistic Locking

Concurrency control in database transactions.

PESSIMISTIC LOCKINGOPTIMISTIC LOCKING
PhilosophyLock first. Assume conflicts will happen; lock the data when it is readCheck first. Assume conflicts are rare; let transactions proceed and check before commit
MechanismRow lock (SELECT //. FOR UPDATE)Version column (or timestamp)
ConcurrencyLower; others waitHigher; no locks while reading
ConsistencyStrongDetected at commit time
DownsidesBlocking, risk of deadlocks, slower under loadMay require retry logic; not suitable for high-conflict data

HOW PESSIMISTIC LOCKING FLOWS

Transaction T1 starts and reads the data.
T1 acquires an exclusive lock on Row A.
T2 tries to read/write Row A and must wait.
T1 commits or rolls back.
The lock is released and T2 proceeds.
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM User u WHERE u.id = :id")
User findByIdForUpdate(@Param("id") Long id);
SELECT * FROM users WHERE id = 1 FOR UPDATE;

HOW OPTIMISTIC LOCKING FLOWS

T1 and T2 both read the same row (version = 1).
Both modify the data in memory.
