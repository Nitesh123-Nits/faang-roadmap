WHY NOT INCREASE THREADS INFINITELY?

Each thread consumes stack memory and scheduler overhead plus CPU switching cost. At high counts the CPU spends more time switching than executing, and throughput drops.

Where reactive is preferred: extremely high concurrency, WebSocket/SSE, stream‐ ing, API gateways, long‐lived connections. Traditional blocking stacks (Spring MVC, Tomcat/Jetty, blocking JDBC) remain where simplicity, stability and ecosystem ma‐ turity matter.

PRACTICAL TUNING APPROACH

Start with the default.
Load test with realistic traffic.
Observe metrics: CPU, memory, latency (p95/p99), throughput, thread pool us‐ age, queue length, DB pool usage.
Identify bottlenecks: DB? External API? CPU? Network?
Tune gradually. Increase threads only if metrics say you need it.

GOLDEN PRODUCTION PRINCIPLE

Never tune thread count blindly. System throughput depends on CPU, memory, DB capacity and pool size, downstream latency, network, and request duration.

TA K E AWAY S . Default Tomcat pool is 200. Big companies scale horizontally, not with thousands of threads in one server. Match the thread pool with the DB pool and downstream capacity. Use reactive only where it truly provides benefit. Measure first. Tune second. Scale smart.
