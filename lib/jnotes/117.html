PESSIMISTIC VS OPTIMISTIC LOCKING

T1 commits with version = 1: success, version becomes 2.

T2 tries to commit with the old version 1: fails (version mismatch).
T2 re‐reads the latest row (v = 2), applies its changes, and retries.
@Entity
public class Product {
    @Id private Long id;
    private String name;
    private BigDecimal price;

    @Version
    private Long version;      // managed automatically by JPA
}
UPDATE product
SET price = 120.00, version = version + 1
WHERE id = 1 AND version = 1;       /- zero rows updated = conflict

HANDLING THE CONFLICT IN JAVA

try {
    repository.save(entity);
} catch (ObjectOptimisticLockingFailureException ex) {
    // reload with latest data and retry
}

K E Y TA K E AWAY. Pessimistic: lock when you read. Optimistic: check before you write. Use pessimistic locking for strong consistency and critical data; use optimistic locking for better performance and high concurrency with low conflicts.
