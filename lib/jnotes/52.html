CHAPTER 33

ThreadPool Rejection Policies

A RejectedExecutionHandler decides what happens when a new task arrives but the pool and its queue are both full.

WHEN IS REJECTION TRIGGERED?

2. 3.

All threads in the pool are busy. The work queue is full. A new task is submitted.

THE FOUR BUILT-IN POLICIES

POLICYWHAT HAPPENSUSE WHEN
AbortPolicyThrowsBanking, payments, order processing, inventory
(default)RejectedExecutionExceptionupdates. Fail fast is better than silently losing work
CallerRunsPolicyThe submitting thread runs the task itselfREST APIs, notification services, batch jobs, event processing. Creates backpressure; slows the producer naturally
DiscardPolicySilently drops the new taskMetrics, logging, analytics, cache refresh, telemetry. Best-effort; losing an occasional task is acceptable
DiscardOldestPolicyDrops the oldest queued task, then enqueues the new oneLive dashboards, stock prices, sensor data, GPS tracking. Newest data is more valuable than older queued work

SCENARIORECOMMENDED POLICY

CUSTOM REJECTION POLICY

When you need to retry, persist, send to a queue, alert, or implement custom logic:

class LoggingRejectHandler implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // Log, send to Kafka, retry, persist to DB, alert, etc.
    }
}

INTERVIEW TIPS

AbortPolicy : critical operations. Fail fast.
CallerRunsPolicy : best for most web apps. Provides backpressure.
THREADPOOL REJECTION POLICIES

DiscardPolicy : only for non‐critical, best‐effort tasks.

DiscardOldestPolicy : real‐time workloads where the latest data matters.
Custom handler: when tasks must be persisted, retried or redirected.

R E M E M B E R . The right policy prevents system overload, data loss and cascading

failures.
