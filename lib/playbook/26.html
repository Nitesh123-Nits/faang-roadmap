REMEMBER
Requirements and numbers before boxes.
Start simple; add components only when forced.
Always ask: what dies, and what is stale?
DEEP DIVE
Clarify requirements. Functional scope, users, read/write ratio, latency, consistency and

availability targets.

Estimate scale. Requests per second, storage, bandwidth.
Define APIs and the data model. Entities, keys, access patterns.
Sketch the high-level architecture. Clients, edge, services, data stores, async paths.
Deep-dive the hardest one or two components (hot path, hot keys, consistency).
Probe failure and scaling. What breaks first? Replication, retries, back-pressure, multi-

region.

Summarise trade-offs and what you would build in version one versus later.

Questions to ask yourself at each box

What happens if this node, zone or dependency dies?
What is the bottleneck at 10× load?
Where can data be stale, and for how long?
How do I observe it: metrics, logs, traces, SLOs?
What is the simplest design that meets the stated need?
SIMPLEST FIRST

Begin with a monolith and one database; add components only when a stated requirement forces them. Each box you add is something you must operate.
