DEEP DIVE

The workload is write-heavy and bursty: huge numbers of tiny events (a swipe is a few bytes) with a matching check on each. The design reflects that.

Location search. Google S2 cells index users so “people near me” becomes a cell lookup.
Key-value / document storage for profiles and relationships, which are accessed by id and need horizontal scale.
Event streaming. Each swipe is published to a stream. A consumer checks whether the other person has already swiped right and, if so, writes a match. This decouples ingestion from matching.
Change data capture propagates table changes to search indexes and analytics without dual writes.
Real-time delivery. Matches and messages are pushed over WebSockets.
Service mesh + API gateway to manage hundreds of microservices: mTLS, retries, timeouts and traffic policy outside application code.

Hot shards

Usage follows time zones, so one region's shards can go hot every evening. Mitigations in the playbook-style toolbox:

Many small shards per server, so load can be rebalanced by moving shards, not splitting them.
Caching absorbs read hot spots.
Rate limiting caps write hot spots from abusive or buggy clients.
Backoff with jitter on failures prevents retries from amplifying overload.
TA K E AWAY

Design for skew, not averages. The busiest shard at the busiest hour is the one that sets your capacity plan.
