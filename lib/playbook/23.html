DEEP DIVE

The dual-write problem

Saving to a database and then publishing to a broker are two separate operations. If the service crashes between them, you have a change with no event, or an event for a change that rolled back.

Transactional outbox Write the business row and an outbox row in the same local transaction. A relay then publishes outbox rows to the broker, either by polling or by change data capture (Debezium reading the database log). Delivery is at-least-once, so consumers must be idempotent: store processed event ids, or make the handler naturally repeatable (upserts).

“Exactly-once” across a broker and an external database is really at-least-once plus idempotent processing. Kafka transactions give atomic read-process-write only between Kafka topics.

Saga A business transaction spanning services (order, payment, inventory) cannot use one ACID transaction. A saga is a sequence of local transactions, each with a compensating action (refund, release stock) run if a later step fails. Choreography lets services react to each other's events; orchestration uses a coordinator that drives the steps and is easier to reason about.

Ordering and partitions

Kafka orders events only within a partition; key by aggregate id so all events of one order stay together.
