How Databases Store Passwords Securely

THE IDEA

Never store the password. Store a slow, salted fingerprint of it.

HOW IT WORKS
1

Password User submits it

2

Salt + slow hash Random per-user value added

3

Store hash & salt Only the fingerprint is kept

4

Re-hash on login Same salt + params used again

5

Compare Constant-time match

REMEMBER
Store a salted, slow hash. Never the password.
Use Argon2id or bcrypt; never plain SHA-256.
Spring: DelegatingPasswordEncoder lets you migrate algorithms.
DEEP DIVE

A database that holds plaintext passwords turns every breach into a catastrophe. The standard defence is to store a one-way fingerprint instead: a hash cannot be reversed, so the server can check a password without ever keeping it.

Why a plain hash is not enough

Attackers precompute hashes of common passwords (a rainbow table) and simply look stolen hashes up. Fast general-purpose hashes such as SHA-256 also let a GPU test billions of guesses per second. Two ingredients fix this:

Salt — a unique random value per user, stored next to the hash. Identical passwords then produce different hashes and precomputed tables become useless.
Work factor — a deliberately slow, tunable algorithm (bcrypt, scrypt, Argon2id, PBKDF2) so each guess costs real CPU time or memory.

Login flow

Look up the user and read the stored salt, parameters and hash.
Hash the submitted password with the same salt and parameters.
Compare the two values in constant time; grant access only if they match.

TRADE-OFF

A slow hash also slows your login endpoint. Rate-limit logins, and tune the cost so one hash takes roughly 100–300 ms on production hardware. An optional pepper (a secret kept outside the database, e.g. in a KMS) adds protection if only the DB leaks.
