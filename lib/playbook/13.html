DEEP DIVE

Lambda runs your function on demand, billing per invocation. Behind the simple API sits a set of cooperating services: a frontend that accepts invocations, a placement service that picks or creates an execution environment, and workers (physical hosts) that run it.

Isolation with microVMs Many customers share a worker, so isolation must be strong. Each execution environment runs inside a Firecracker microVM: a minimal virtual machine that boots in a fraction of a second with a tiny memory footprint, giving VM-level isolation at near-container density.

The cold start problem A cold start is the time to create an environment, download code, start the runtime and run your init code. Lambda attacks it in layers:

Reuse. After a run, the environment is kept warm for later invocations, so later calls skip all setup.
Snapshots. Initialised environments can be snapshotted and restored, rather than booted from scratch. For Java this is exposed as SnapStart.
Lazy, deduplicated image loading. Container images are fetched in chunks on demand, and chunks shared across layers and customers are cached instead of re-downloaded.
Provisioned concurrency keeps a number of environments pre-initialised if you need guaranteed low latency.

Fault tolerance Control-plane state, such as which worker owns which environment, is kept in replicated, journaled stores so a failed component can be replaced without losing track of running work.

FOR JAVA DEVELOPERS

JVM cold starts are the weak spot. Reduce them with SnapStart, GraalVM native image, fewer or lazier beans (Spring Cloud Function, or Micronaut/Quarkus), and a lean dependency set. Beware of state captured in a snapshot: refresh connections, random seeds and credentials after restore.
