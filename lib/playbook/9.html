How Figma Scaled Postgres

THE IDEA

A scaling ladder: bigger box, replicas, cache, pooling, vertical then horizontal partitioning.

HOW IT WORKS
1

Scale up Bigger instance

2

Read replicas + cache Replicas and a cache

3

PgBouncer pooling Pool connections

4

Vertical partition by domain Split tables by domain

5

Horizontal shard by key Split one table by key

REMEMBER
Climb the cheap steps first; shard last.
Pooling and caching postpone sharding for years.
Pick a high-cardinality, even shard key.
DEEP DIVE

Figma's journey is a textbook example of doing the cheap thing first. They stayed on PostgreSQL and climbed a ladder, only reaching for sharding when simpler steps ran out.

Scale up. A larger instance buys time at almost no engineering cost.
Read replicas absorb read traffic and give failover capacity. Beware replication lag for

read-your-writes.

Caching in front of the database removes the hottest reads entirely.
Connection pooling (PgBouncer) prevents connection starvation, since each Postgres

connection is a process.

Vertical partitioning moves whole tables or domains onto separate databases, so one

noisy feature cannot starve another.

Horizontal sharding splits a single huge table by key across many databases. It brings

routing logic, hard cross-shard queries and migration risk.

Practical points

Pick a shard key with high cardinality and even spread (a tenant or file id, not a timestamp).
Build a logical sharding layer before the physical one, so you can roll back.
Move data with dual writes, backfill and verification, then cut over per shard.
Tables that join frequently should share a shard key to stay co-located.
CHALLENGE TO THE USUAL INSTINCT

Most teams shard too early. A properly indexed, well-pooled Postgres with replicas and a cache carries a surprising amount of load. Shard when write throughput or dataset size, not read volume, is the proven bottleneck.
