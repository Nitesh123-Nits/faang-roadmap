DEEP DIVE

As traffic grew, YouTube kept MySQL but added a layer above it. That layer, Vitess, was written in Go, open-sourced, and now underpins many large deployments. The idea: keep the proven storage engine, move scaling concerns into a purpose-built middle tier.

Main components

VTGate — a stateless proxy that speaks the MySQL protocol, parses queries, and routes or scatter-gathers them to the right shards. It also pools connections.
VTTablet — a sidecar next to each MySQL instance. It enforces query limits, rewrites risky queries (for example adding a LIMIT ), and deduplicates identical in-flight reads so a hot row cannot cause a stampede.
Topology service — a small strongly consistent store (etcd, ZooKeeper) holding shard maps and tablet state.
VSchema — declares the sharding key and how tables are distributed.

Why it works

Connection pooling. MySQL handles thousands of connections poorly; the proxy multiplexes many clients onto few backend connections.
Query protection. One runaway query is killed or bounded before it takes down a primary.
Resharding online. Data can be split or merged while serving traffic.
Replicas for reads and automated failover for availability.
TRADE-OFF

Cross-shard joins, transactions and unique constraints become expensive or limited. Choose a shard key that keeps most queries on one shard, and accept eventual or twophase semantics for the rest. If you are on managed MySQL, PlanetScale is Vitess as a service.
