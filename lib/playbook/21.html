DEEP DIVE

Networks fail ambiguously: a timeout does not tell you whether the charge happened. If the client retries a plain POST /charges , the customer may be billed twice. An idempotent operation can be repeated with the same effect as doing it once.

The idempotency-key protocol

The client generates a unique key (a UUID) per logical operation and sends it in an

Idempotency-Key header.

The server looks the key up in a store. If it is new, the server records it, performs the

work and saves the response (status and body) against the key.

On a retry with the same key, the server returns the saved response without running the

work again.

If the same key arrives with a different payload, reject it, because this signals a client

bug.

Keys expire after a window (Stripe documents 24 hours), after which they can be reused.

Details that matter

Atomicity. The key record and the business change must commit together, ideally in one database transaction. A unique constraint on the key makes concurrent duplicates fail

safely.

In-flight requests. Mark a key processing; a concurrent duplicate waits or gets 409 .
Server errors. Roll back on failure so the key does not store a half-done result.
Downstream calls (the card network) need their own idempotency or a reconciliation job.
