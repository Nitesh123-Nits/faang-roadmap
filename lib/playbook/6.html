How Amazon S3 Works

THE IDEA

An object store built from many small services, a metadata index and a lot of disks.

REMEMBER
Index (metadata) and bytes scale separately.
Flat keys, not folders; parallel disks give throughput.
Pre-signed URLs let clients upload directly.
DEEP DIVE

S3 stores objects (a blob plus metadata) in flat buckets. There is no real directory tree; a key like logs/2026/11/app.log is just a string. That simplicity is what lets it scale to trillions of objects.

Separate the index from the bytes A request is handled by a fleet of stateless front-end services. They authenticate the caller, consult a metadata subsystem (a replicated key-value index that maps a key to where its data lives), and read or write to a separate storage layer of disk servers. Splitting the two lets each scale on its own axis: index size and request rate on one side, raw capacity and throughput on the other.

Choices worth noticing

Commodity hard disks for cost, with software providing the reliability. Sequentialfriendly on-disk layouts hide the seek penalty.
Log-structured storage on each disk (AWS describes a custom store called ShardStore) so writes append rather than update in place.
Parallelism — one object spans many disks, so reads pull from several at once.
Erasure coding instead of full copies to cut storage overhead (next chapter).
Strong read-after-write consistency since 2020, for new objects and overwrites.

Using it well

Spread key prefixes sensibly; S3 scales request rate per prefix.
Use multipart upload for large objects, with parallel parts and retry per part.
Use pre-signed URLs so clients upload directly and your service never proxies bytes.
IN SPRING

Prefer the AWS SDK v2 S3Client / S3TransferManager , or Spring Cloud AWS S3Template . Generate a pre-signed PUT URL in your API and let the browser or mobile app upload straight to S3.
