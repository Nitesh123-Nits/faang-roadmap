THE PAPER IN ONE LINE

Run a NoSQL database for everyone by pairing leader-based Paxos replication with admission control that keeps latency predictable.

IN EVERYDAY TERMS

A shared swimming pool with lane tickets. Each swimmer gets a fixed number of tickets per second. A heavy swimmer cannot take over the pool and slow everyone else down. That ticket system is what makes the pool’s speed predictable.

THE PROBLEM

DynamoDB is a fully managed NoSQL service. The paper’s thesis: customers care less about peak speed than about predictable performance, the same single-digitmillisecond latency for the first request and the billionth, regardless of table size or what the neighbours are doing.

Not the 2007 Dynamo

Despite the name, DynamoDB is not Dynamo (Chapter 8) running as a service. Its replication is leader-based, not leaderless.

THE BIG IDEA

route → check capacity → leader replicates across zones

Life of a write: route, check capacity, then leader-based replication across Availability Zones.

A table is split into partitions, each owning a contiguous key range, replicated across three Availability Zones.
Replicas form a group using Multi-Paxos. The leader holds a renewable lease and serves writes and strongly consistent reads.
Log replicas store only recent write-ahead-log entries, no data. They take part as acceptors and make healing cheaper.
Request routers authenticate, authorize and route each call using a metadata service.
An auto-admin service watches fleet health, replaces bad replicas and splits partitions.

Predictability: from provisioned capacity to global admission control

Customers buy read capacity units (one strongly consistent read per second, up to 4 KB) and write capacity units (one write per second, up to 1 KB). Enforcing that fairly across a shared fleet took several generations:

Admission control with token buckets, the mechanism behind “predictable performance”.

Partition-level limits Each partition got a share of the table’s capacity. Problem: a hot partition was throttled even though the table had spare capacity.
Bursting A partition can use unused capacity, retained for up to 300 seconds, to absorb spikes.
Adaptive capacity Boosted skewed partitions. The paper says it removed over 99.99% of throttling from skewed access.
Global admission control Request routers hold token buckets for the table and refill them from a central service every few seconds. Partition-level throttling stays as a safety net.

Operational lessons the paper shares

Metadata caches hide a failure mode. When routers’ caches were cold, metadata traffic could spike to about 75% and overload the service. They replaced the caches with an in-memory distributed store (MemDS), so lookups stay fast and traffic stays steady. The original cache hit rate was about 99.75%.
Backups never touch live traffic. Full backups are built from archived write-ahead logs in S3.
On-demand mode can instantly serve up to double a table’s previous peak.
Transactions: multi-item ACID transactions were added without hurting scalability or availability.

WHAT IT GIVES UP
The model is limited: you design access patterns around your keys.
A hot key still hits one partition’s limits.
Cost scales with provisioned throughput or on-demand usage.
USE IT IN YOUR WORK

Your own APIs need admission control too. A token bucket per tenant (see Spring Cloud Gateway or Bucket4j) stops noisy neighbours. And watch for modal behaviour: a design that is fast only when a cache is warm will fall over exactly when you restart.

SAY IT IN AN INTERVIEW

“DynamoDB gives predictable single-digit-ms performance through partitioned Multi-Paxos groups across three AZs, plus layered admission control: token buckets, burst capacity and global admission control.”

IF YOU REMEMBER ONE THING

Predictable beats fast: protect every tenant from every other tenant.
