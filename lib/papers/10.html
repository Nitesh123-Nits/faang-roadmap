WHAT IT GIVES YOU The mental model behind batch and stream processing

THE PAPER IN ONE LINE

Express a huge computation as map then reduce, and let the runtime handle partitioning, scheduling and failures by simply re-running tasks.

IN EVERYDAY TERMS

Counting votes in a huge election. Hundreds of clerks each count one box and write tallies per candidate (map). Then all tallies for the same candidate go to one person who adds them up (reduce). If a clerk falls ill, someone else just recounts that box.

THE PROBLEM

Google engineers wrote many small programs to process huge data: crawled pages, logs, inverted indexes. The computation was simple; the plumbing was not. Splitting data, spreading work over thousands of machines, surviving failures, moving data between stages. The authors extracted that plumbing into a library.

THE BIG IDEA

You write two functions. The framework does everything else.

map(key, value)

Reads one piece of input and emits intermediate (key, value) pairs.

reduce(key, [values])

Combines all values that share one key into a result.

Think of it in Java terms

Map<String, Long> counts = lines.stream()
    .flatMap(l -> Arrays.stream(l.split(" ")))   // map
    .collect(groupingBy(w -> w, counting()));    // shuffle + reduce

Same shape, except MapReduce runs it over terabytes on thousands of machines.

How a job runs

Split the input The input is cut into splits (the paper mentions 16–64 MB). A master hands splits to idle workers, preferring one that already holds the data on its local disk.
Map Map workers write results to local disk, partitioned into R buckets with hash(key) mod R .

Shuffle and reduce Reduce workers fetch their bucket from every map worker, sort by key, and call reduce.

Write the output Reduce outputs go to the distributed file system (GFS, Chapter 4).

Fault tolerance: just run it again

Worker dies: the master notices missed pings and re-runs its tasks. Even finished map tasks are re-run, because their output sat on the dead machine’s local disk.
Safe re-execution: deterministic functions plus an atomic rename of output mean duplicates do no harm.
Stragglers: near the end of a job, the master launches backup copies of the slowest tasks. Whichever finishes first wins.
Bad records: the framework can skip input records that repeatedly crash the user code.
Master failure: the simple answer is to abort and re-run the job.

Smart optimisations

Combiner

A mini-reduce on the map side (for example, pre-summing word counts) to shrink the shuffle.

Locality

Move computation to the data, not data to the computation. Network bandwidth was the scarce resource.

Partition function

Controls which reducer gets which key. Skewed keys mean one slow reducer.

Ordering

Within a partition, keys are processed in sorted order.

KEY TERMS
ShuffleMoving map output so all values with the same key meet at one reducer.
StragglerA task that runs much slower than its peers and delays the whole job.
IdempotentSafe to run twice: the result is the same as running once.
WHAT IT GIVES UP
Every stage writes to disk and the shuffle is all-to-all, so chained or iterative jobs are slow. That gap led to in-memory engines like Spark.
One hot key sends all its values to one reducer.
USE IT IN YOUR WORK

Build batch jobs from idempotent, deterministic tasks so any task can be retried safely. That is the design rule behind retries in Kafka consumers, Spring Batch restarts and your own backfills.

SAY IT IN AN INTERVIEW

“MapReduce hides distribution behind map and reduce. Fault tolerance comes from deterministic tasks that can be re-executed, and backup tasks fix stragglers.”

IF YOU REMEMBER ONE THING

If a task can be safely repeated, failure stops being scary.
