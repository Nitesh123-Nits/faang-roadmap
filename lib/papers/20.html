THE PAPER IN ONE LINE

A cache is a distributed system too: look-aside reads, delete-on-write, leases for stampedes, and invalidation streams from the database log.

IN EVERYDAY TERMS

A popular dish at a canteen is kept ready at the counter (the cache). When the recipe changes, you throw away the old batch instead of trying to edit it, so no one is served a half-updated plate. And if a thousand people ask for a dish that just ran out, only one person goes to the kitchen.

THE PROBLEM

Facebook’s workload was overwhelmingly reads: pages assembled from many small pieces of data fetched from MySQL. The paper’s headline: their memcache deployment handles billions of requests per second and holds trillions of items. The authors describe growing a simple in-memory cache from one cluster, to many clusters, to many regions, and what broke at each step.

Step 1: one cluster, look-aside caching

READ 1 try the cache 2 on a miss, read MySQL 3 fill the cache

WRITE 1 update MySQL 2 DELETE the cached key (never "set" it) 3 next read refills it

The cache is dumb; the app and database do the work. Deleting on write keeps it simple and safe.

Delete is idempotent; “set” can race and leave stale data. So after updating the database, you delete the cached key and let the next read refill it.

Clients do the work. A client library (and a proxy called mcrouter) handles routing and batching, so servers stay simple. Gets use UDP to reduce overhead; sets and deletes use TCP. A sliding window limits in-flight requests to avoid network congestion on fan-in (“incast”).

Two problems solved by leases

A lease token fixes stampedes and stale sets at the same time.

Stale set

A slow client writes an old value after a newer delete. A set with an invalidated token is rejected.

Thundering herd

A hot key is deleted and thousands of readers rush to the database. Only one reader gets the lease; the others are told to wait briefly.

The paper rate-limits lease tokens per key (by default one every 10 seconds).

Surviving failures: pools and gutters

Pools

Different workloads get separate memcache pools, so a churny low-value workload cannot evict valuable data.

Gutter

A small pool of idle machines takes over for failed servers. Gutter entries expire quickly instead of being invalidated, protecting the database during outages.

Steps 2 and 3: many clusters, many regions

Invalidation pipeline: a daemon (McSqueal) reads the MySQL commit log and broadcasts the deletes to every cache cluster. Applications need not remember every place to invalidate.
Regional pools: rarely accessed, bulky data is cached once per region instead of once per cluster, to save memory.
Cold cluster warm-up: a new empty cluster can fetch from a warm one instead of hitting the database.
Across regions: one region holds the master databases; others replicate from it. After a write in a replica region, a remote marker tells reads to go to the master region until replication catches up. That trades latency for avoiding a stale read of your own write.

WHAT IT GIVES UP
Consistency is eventual and carefully bounded, not strong. The paper’s guiding principle is explicit: allow some stale reads in exchange for scale.
The system needs significant operational tooling, and every invalidation path is a place where a bug becomes stale data.
USE IT IN YOUR WORK

concurrent misses. Delete on write rather than updating. Add jitter to TTLs so a million keys do not expire together. Consider a fallback layer so a failing cache does not stampede your database.

SAY IT IN AN INTERVIEW

“Facebook used look-aside memcache with delete-on-write. Leases stop stale sets and thundering herds, gutter pools absorb failures, and a commit-log invalidation daemon keeps clusters and regions eventually consistent.”

IF YOU REMEMBER ONE THING

Delete, never overwrite; and let only one client refill a hot key.
