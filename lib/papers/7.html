THE PAPER IN ONE LINE

Make consensus teachable: one strong leader, randomized election timeouts, and a log that only moves forward.

IN EVERYDAY TERMS

A meeting with a chair. Everyone talks to the chair, and the chair announces decisions. If the chair goes quiet, someone clears their throat and calls a vote, and whoever gets a majority becomes the new chair. Raft is that meeting, written as an algorithm.

THE PROBLEM

By 2014 Paxos was the standard answer to consensus, yet students and engineers found it hard, and real systems built from it often looked very different from the paper. Raft’s goal was unusual for a systems paper: design for understandability first, with the same fault tolerance and similar performance.

THE BIG IDEA

Raft splits consensus into three smaller problems: leader election, log replication and safety. At any moment one server is the leader. Clients talk to it, and log entries flow one way only: leader → followers.

HOW IT WORKS

Three states, and elections

Every Raft server is always in exactly one of three states.

Wait for heartbeats A follower expects regular messages from the leader.
Time out If none arrive within its election timeout, it becomes a candidate, adds 1 to the term number, and asks for votes.
Win a majority A majority of votes makes it the leader. Each server votes once per term.

Lead The new leader sends heartbeats immediately so nobody else starts an election.

The trick that avoids endless split votes

Each server picks a random timeout from a range (the paper suggests 150–300 ms). Usually exactly one server wakes first, wins, and sends heartbeats before anyone else wakes up.

Replicating the log

The leader appends the client’s command to its log and sends AppendEntries to followers. This same message doubles as the heartbeat. Each message names the entry just before the new ones. A follower that lacks it refuses, and the leader walks backwards until the logs match, then overwrites any conflicting tail.

Safety: the two rules people forget

Election restriction

A server votes only for a candidate whose log is at least as up to date as its own (last term first, then length). So a new leader always holds every committed entry.

Commit rule

A leader never commits entries from earlier terms by counting replicas. It commits one entry from its own term, and that commits everything before it.

Membership changes and snapshots

To add or remove servers, Raft uses joint consensus: during the change, decisions need majorities of both the old and new configurations, so two independent leaders can never exist. Long logs are trimmed with snapshots.

KEY TERMS
TermA numbered period with at most one leader. It acts as a logical clock.
AppendEntriesThe leader’s message that carries new log entries and also acts as a heartbeat.
CommittedStored on a majority, so it can never be lost.
State machineThe service that applies committed commands in order.
WHAT IT GIVES UP
All writes go through one leader, so write throughput is limited by it. Scaling means many Raft groups (sharding), which is what Spanner and DynamoDB do with Paxos groups.
Outside the paper: etcd and Consul are built on Raft, and Kafka’s KRaft mode uses a Raft-based quorum for metadata in place of ZooKeeper.
USE IT IN YOUR WORK

When you design a replicated component, define states, terms (epochs) and one writer. An epoch number that fences old leaders is the same idea as a fencing token for distributed locks (Chapter 7).

“Raft elects a leader with randomized timeouts, replicates a log with AppendEntries, commits on majority, and uses an election restriction so a new leader always holds all committed entries.”

IF YOU REMEMBER ONE THING

One leader, one direction of flow, and a vote that only goes to an up-to-date log.
