THE PAPER IN ONE LINE

One replicated brain and a small agent per machine can run an entire company’s workloads at high utilization, if scheduling, quota and priorities are done right.

IN EVERYDAY TERMS

A hotel manager assigning guests to rooms. VIP bookings are placed first. Cheaper guests fill what is left, and can be moved if a VIP arrives. Each floor has a supervisor reporting back to the manager. Borg is that hotel, with machines as rooms.

THE PROBLEM

Google runs hundreds of thousands of jobs from many thousands of applications across clusters of up to tens of thousands of machines. Borg is the internal cluster manager that decides where each piece of work runs, restarts it when machines fail, and keeps the hardware busy. This is the paper that explains the ancestry of Kubernetes.

A logically centralized, replicated brain and a small agent on every machine.

A cell is a set of machines managed as one unit (the median is about 10,000 machines).
Users submit jobs, each made of one or more tasks that run in containers. The spec is declarative: “run 200 of these, 2 GB each, priority X”.
The Borgmaster is replicated five times with a Paxos-elected leader. On every machine, a Borglet starts and stops tasks and reports health.
Allocs reserve resources on a machine into which several tasks can be placed (the ancestor of the Kubernetes pod).
Naming and monitoring are built in: tasks get stable names, and jobs have realtime monitoring.

Scheduling: two steps

Highest-priority (production) work is placed first; batch work soaks up leftover capacity.

Feasibility finds machines that meet the task’s constraints and have enough resources (counting resources that could be freed by preempting lower-priority tasks). Scoring then picks among them, balancing goals such as spreading across failure domains, packing machines tightly, and minimizing disruption.

How Borg keeps utilization high

Admission control and quota: users get a quota per priority; jobs above quota are rejected at submission.
Priorities and preemption: production services outrank batch; batch soaks up leftover capacity and is preempted when needed.
Over-commitment and reclamation: tasks request generous limits, but the system estimates actual use and lends the unused remainder to low-priority work.
Prod and batch share machines, with process-level performance isolation.

Built for availability

Failed tasks are rescheduled automatically. The scheduler avoids placing a job’s tasks together where one failure would take them all. Running tasks continue even if the Borgmaster or a Borglet is briefly down.

Lessons the authors learned

What they would change

Jobs as the only grouping mechanism is restrictive (Kubernetes uses labels). One IP per machine complicates things (Kubernetes gives each pod its own IP). The system favoured power users over casual ones.

What held up

Allocs are useful. Cluster management is more than task management. Introspection is vital. The master is the kernel of a distributed system, so keep it a clean API.

WHAT IT GIVES UP
Borg is a centrally scheduled, tightly co-designed system, with complexity in the scheduler and in resource estimation.
Over-commitment means an occasional unlucky co-location, which is why tasks must handle preemption.
USE IT IN YOUR WORK

In your Spring Boot deployments, requests are reservations and limits are ceilings: set both honestly. Use readiness probes so traffic only reaches healthy pods, PodDisruptionBudgets to keep replicas alive during maintenance, and expect every task to be killed and restarted at any time.

SAY IT IN AN INTERVIEW

“Borg is a Paxos-replicated master plus per-machine agents. It schedules by feasibility then scoring, uses priorities, quota and resource reclamation for high utilization, and Kubernetes carries its core ideas.”

IF YOU REMEMBER ONE THING

Reserve honestly, prioritise clearly, and assume every task will be restarted.
