WHAT IT GIVES YOU Tunable consistency and the “always writable” philosophy

THE PAPER IN ONE LINE

Choose availability over strong consistency: replicate on a ring, accept writes anywhere, keep versions with vector clocks, and merge later.

IN EVERYDAY TERMS

Two people add items to the same shared shopping list on separate phones, with no signal. Both lists are valid. Dynamo’s answer: do not block either person. When they reconnect, keep both versions and merge them, so nothing is lost.

THE PROBLEM

On Amazon’s e-commerce platform, an unavailable shopping cart means lost orders. Service-level agreements were written at the 99.9th percentile, not the average. The paper cites a typical SLA of 300 ms for 99.9% of requests at a peak of 500 requests per second.

Amazon’s engineers concluded that for many services, availability matters more than strict consistency. So Dynamo is always writable: it accepts writes even during failures and resolves conflicts later.

THE BIG IDEA

Keys and nodes are hashed onto a ring. The first node clockwise from the key is its coordinator, and the key is also stored on the next N − 1 nodes. Every node can coordinate; there is no leader.

Three copies (N = 3). A write needs 2 acks (W = 2); a read asks 2 replicas (R = 2).

Each physical node owns many small ring positions (virtual nodes), so load is even, stronger machines can take more, and a failed node’s work spreads over many peers.

HOW IT WORKS

Quorums you can tune

A write succeeds after W replicas acknowledge. A read asks R replicas. With R + W > N the sets overlap, so a read normally sees the latest write. The paper’s common setting is (N, R, W) = (3, 2, 2) . Lower W for faster writes, lower R for faster reads, and accept some staleness.

Sloppy quorum

If one of the N home nodes is down, Dynamo writes to the next healthy node on the ring with a hint saying whose data it is. When the owner returns, the hint is handed back. You stay available, but you give up the strict overlap guarantee.

Versioning with vector clocks

Two clients update the cart at the same time while the network is split.

Each version carries a vector clock: a list of (node, counter) pairs. If one clock covers another, the older version is dropped. If neither does, they are siblings and both are returned to the client to merge. In production, 99.94% of requests saw exactly one version.

Healing: gossip and Merkle trees

Nodes gossip membership and failure information with random peers.
Replicas compare Merkle trees (hash trees) of their key ranges, so they find differing data by exchanging a few hashes, not whole datasets.

WHAT IT GIVES UP
Conflict resolution leaks into application code, and a classic anomaly is that a removed cart item can reappear.
Every node keeping routing information about all others limits how far the design scales.
Dynamo was an internal system, not a product. DynamoDB (Chapter 11) is a very different design: a leader-based Paxos group per partition.
USE IT IN YOUR WORK

Treat (replicas, write quorum, read quorum) as per-use-case knobs, make writes idempotent, and decide up front how conflicts merge: last-write-wins, union, or CRDT-style. Read repair and hinted handoff reappear in Cassandra (Chapter 9).

SAY IT IN AN INTERVIEW

“Dynamo trades consistency for availability: consistent hashing with virtual nodes, N/R/W quorums, sloppy quorum with hinted handoff, vector clocks, and Merkle-tree anti-entropy. It never blocks writes.”

IF YOU REMEMBER ONE THING

Never refuse a write; keep every version and merge when you can.
