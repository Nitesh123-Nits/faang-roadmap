THE PAPER IN ONE LINE

Store giant files on cheap machines by keeping metadata in one inmemory master and moving the data directly between clients and replicas.

IN EVERYDAY TERMS

A library with one librarian and many shelves. The librarian never carries books; they only keep the catalogue, in their head, of which shelf holds what. You ask the librarian where a book is, then walk to the shelf yourself. GFS works the same way.

THE PROBLEM

Google needed storage for crawling and indexing the web: files of many gigabytes, thousands of cheap machines, and a workload that mostly appends and reads sequentially. The authors built around four observations:

Failures are normal on commodity hardware, not exceptional.
Files are huge (multi-GB), so small-file tricks matter little.
Mostly append and sequential read. Random overwrites are rare.
Co-design file system and applications, so the API can be relaxed (for example, an atomic record-append).

Files are cut into fixed 64 MB chunks. Each chunk has an immutable 64-bit ID, is stored as a plain Linux file on a chunkserver, and is copied to three machines by default (spread over racks).

One master keeps all metadata in memory: the file names, the file-to-chunk mapping, and where each chunk lives. Clients ask the master only where, then read and write the data directly with chunkservers. The bytes never pass through the master.

HOW IT WORKS

Control (orange, dashed) goes through the master. Data (slate) goes straight between client and chunkservers.

A write, step by step

Ask the master The client asks which chunkserver holds the lease (the primary) for the chunk.
Master replies It returns the primary and the replicas. The client caches this.
Push the data The client sends the data to the nearest replica, which forwards it down a chain.

Write request The client then tells the primary to perform the write.

Primary orders it The primary gives the write a serial number and tells the secondaries to apply it.
Acknowledge Secondaries confirm to the primary, and the primary confirms to the client.

Why one master is enough (the metadata math)

The master stores under 64 bytes of metadata per 64 MB chunk. As a back-ofenvelope, 1 PB is about 16.8 million chunks, so roughly 1 GB of RAM per petabyte. It does not even persist chunk locations: it simply asks chunkservers through heartbeats. Changes go to a replicated operation log, plus checkpoints. Read-only shadow masters serve reads if the master is down.

Relaxed consistency, on purpose

Record append lets many clients append to the same file at once. GFS chooses the offset and guarantees the record lands at least once. Duplicates and padding are possible, so applications write self-validating records with checksums or unique IDs.

Running a cluster that always has failures

Re-replication: in one failure test, about 15,000 chunks (600 GB) were restored in 23.2 minutes.
Garbage collection: deleted files are renamed, then reclaimed lazily (hidden files are removed after three days by default).
Integrity: chunkservers checksum every 64 KB block and verify on read.

WHAT IT GIVES UP
The single master is a bottleneck and a single point of failure by design. It works for big files and modest metadata; Google later moved to a successor system as scale grew.
Large chunks hurt small files: one hot small file lives on one chunk, so a few servers get hammered.
USE IT IN YOUR WORK

Separate the control plane from the data plane. A metadata service decides; storage nodes move bytes. The same split shows up in HDFS (NameNode and DataNodes) and in object-store designs where your service hands out pre-signed URLs and never proxies large files.

SAY IT IN AN INTERVIEW

“GFS keeps all metadata in one master’s memory and lets clients stream data directly to chunkservers. 64 MB chunks keep metadata tiny, and leases give a single primary per chunk to order writes.”
