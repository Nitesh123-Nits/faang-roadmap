THE PAPER IN ONE LINE

Combine Paxos-replicated shards, two-phase commit and GPS/atomicclock timestamps with bounded error to get globally consistent transactions.

IN EVERYDAY TERMS

Two judges in different countries stamp rulings. Their watches may differ by a few milliseconds, so each judge says: “it is somewhere between 10:00:00.001 and 10:00:00.007”, and waits out the uncertainty before announcing. Now any later ruling, anywhere, is guaranteed a later stamp.

THE PROBLEM

Bigtable gave scale but only single-row transactions. Google’s ads database (F1) needed real transactions across rows and data centres, SQL-like queries, and replicas spread around the world. Spanner is the first system the paper claims distributes data at global scale and still supports externally consistent distributed transactions.

External consistency in one sentence

If transaction T1 finishes before T2 starts in real time, then T1’s commit timestamp is smaller than T2’s. Everyone, anywhere, sees them in that order.

Spanner = many Paxos groups (for replication) + two-phase commit across groups (for transactions).

Data is sharded into tablets; each tablet has a Paxos group with replicas in different zones. Leaders hold leases (10 s by default).
A directory is a set of contiguous keys sharing a prefix, the smallest unit of placement. The paper estimates a 50 MB directory moves in a few seconds.
A spanserver handles 100–1,000 tablets. Zones have from a hundred to several thousand spanservers.
Data is semi-relational: schematised tables, SQL-like queries, and versioned values stamped with commit time.
HOW IT WORKS

TrueTime: admitting that clocks are uncertain

Instead of returning one time, TrueTime returns an interval [earliest, latest] that is guaranteed to contain the true time. It relies on GPS receivers and atomic clocks in

every data centre. The uncertainty ε is typically a sawtooth of about 1–7 ms, around 4 ms most of the time, and generally under 10 ms.

TrueTime does not say what time it is; it says the time is somewhere inside a small interval.

Pick a timestamp The leader picks a commit timestamp s equal to the latest edge of the interval.
Wait It waits until TT.after(s) is true. The expected wait is at least 2ε.
Release Now s is definitely in the past everywhere, so any transaction that starts later gets a larger timestamp. Locks are released and the client is told.

The whole trick

Pay a few milliseconds of waiting, and get externally consistent, global transactions.

WHAT IT GIVES UP
Needs special clock hardware and operations expertise.
Every write pays the commit wait plus Paxos round trips; multi-region writes cost tens of milliseconds.
Pessimistic locking means contended rows hurt.
USE IT IN YOUR WORK

When you need strong consistency, you pay in latency, so offer clients a choice: strong reads versus bounded-staleness reads. The same trade-off shows up in Cloud Spanner, DynamoDB’s strongly versus eventually consistent reads, and Cassandra’s consistency levels.

SAY IT IN AN INTERVIEW

“Spanner shards data into Paxos groups, uses two-phase commit across groups, and TrueTime’s bounded clock error plus commit wait to assign timestamps that respect real-time order, giving external consistency.”

IF YOU REMEMBER ONE THING

Do not pretend you know the time. Bound the error, then wait it out.
