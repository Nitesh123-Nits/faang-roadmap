THE PAPER IN ONE LINE

Instead of giving everyone a consensus library, give them a Paxosbacked lock service with a file API, and let coarse locks do the coordination.

IN EVERYDAY TERMS

A single sign-in sheet at the front desk of a huge company. Whoever signs on the “team lead” line is the lead, and everyone can read the sheet. Nobody has to run their own election. Chubby is that sheet, kept safe by five copies.

THE PROBLEM

Every distributed service at Google needed a way to elect a master or agree on small pieces of configuration, and teams were tempted to write their own consensus code (usually badly). Burrows’ answer: build one shared, highly available lock service that everyone calls, like a very small, very reliable file system.

Why a lock service, not a consensus library?

Developers already understand locks and files, so existing programs need few changes.
A service that starts single-server can later be replicated without rewriting the client.
Small files also let you announce results (who is the master?), not only agree on them.
THE BIG IDEA

/ls/cell/bigtable/master-lock ← whoever holds this lock is the master

A tiny, highly available, replicated file system used mostly as a lock and naming service.

A cell of 5 replicas elects a master using Paxos. The master holds a lease of a few seconds. Three replicas must be up for the cell to work.
A file-like API: whole-file reads and writes of small files, advisory read/write locks, and event notifications.
Coarse-grained locks: held for hours or days, not milliseconds. So the service sees little traffic and can tolerate short outages.
Sessions and KeepAlive: a client’s session is extended by periodic KeepAlive calls (default 12 s). If the master fails over, a 45 s grace period lets sessions survive.
Consistent caching: clients cache files, and the master invalidates caches on a write instead of relying on timeouts.

Locks are not safe on their own: sequencers

A client holding a lock can pause (garbage collection, network trouble) and wake up after the lock expired and went to someone else. Chubby’s answer is the sequencer: a token describing the lock and its generation. The protected server checks it and rejects stale holders. Today we call this a fencing token.

UPDATE job SET owner = :me, token = :t
 WHERE id = :id AND token < :t;     -- 0 rows updated → I lost the lock

What operating it taught them

People misuse shared services. One team rewrote a 1.5 MB file on every user action, which led to the 256 kB file limit and quotas.
Outages were mostly short: over about 700 cell-days there were 61 outages. Most lasted 15 seconds or less, and 52 were under 30 s.
Keep it cheap: KeepAlives dominate traffic, so clients and proxies can multiplex them.

KEY TERMS
LeaseA permission that expires unless renewed.
SessionA client’s ongoing relationship with the cell, kept alive by KeepAlive.
Advisory lockA lock that is only respected by programs that choose to check it.
Fencing tokenA number that only grows. Servers reject requests with an older number.
WHAT IT GIVES UP
It is a central service. Its failure affects many systems at once, so it is run conservatively.
Locks are advisory, not enforced, and clients must handle “jeopardy” and expired sessions.
USE IT IN YOUR WORK

Use fencing in your own code. With any lock (Redis, ZooKeeper, a database row), carry a monotonically increasing token and reject writes with an older one. Never assume that holding a lock means you still hold it when you write.

SAY IT IN AN INTERVIEW

“Chubby is a Paxos-replicated lock and small-file service. Coarse-grained locks, sessions and sequencers give leader election and naming without every team building consensus.”

IF YOU REMEMBER ONE THING

A lock is only safe if the resource it protects can reject a stale holder.
