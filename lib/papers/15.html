THE PAPER IN ONE LINE

A leaderless, always-on database that distributes like Dynamo and stores like Bigtable, built to power Inbox Search.

IN EVERYDAY TERMS

Take the delivery network of one company (any branch can take an order, no head office) and the warehouse of another (everything is logged first, then filed in sorted crates). Cassandra is the two combined.

THE PROBLEM

Facebook’s Inbox Search had to index messages for hundreds of millions of users: billions of writes per day, growth by adding commodity machines, and no single point of failure. The Cassandra paper describes a system for it, built from the best parts of two famous designs.

THE BIG IDEA

Distribution: the Dynamo half

Partitioning: consistent hashing on a ring with an order-preserving hash. A key’s coordinator is the next node clockwise. Instead of virtual nodes, lightly loaded nodes move on the ring to relieve busy ones.
Replication: each item lives on N nodes. Strategies: rack-unaware, rack-aware, and datacenter-aware (survive a whole data centre).
Membership: a gossip protocol, so every node learns about the others with no central registry.
Failure detection: the φ accrual detector outputs a suspicion level from observed heartbeat timing, instead of a hard yes or no.

Storage: the Bigtable half

The log-structured write path: writes are sequential appends, so they are fast. Reads pay for it.

Commit log on a dedicated disk (sequential appends) gives durability. It is rolled at 128 MB.
Memtable is updated only after the log write succeeds, then flushed to an immutable SSTable when it crosses a size threshold.
SSTables carry a block index and an in-memory Bloom filter, so most reads touch very few files.
Compaction merges SSTables in the background. It is disk-heavy, but keeps reads fast.

The data model

A table is a distributed multidimensional map indexed by a row key (typically 16–36 bytes). Operations on a single row key are atomic per replica. Columns live in column families, either simple or super (a column family inside a column family). Inbox Search used super columns: for term search a word maps to message IDs; for interaction search a recipient maps to message IDs.

Then vs. now

The paper dates from Facebook’s time with the system. Today’s Apache Cassandra has evolved: it no longer relies on ZooKeeper for range assignment, and its default partitioner hashes keys rather than preserving order. Treat the paper as the origin story and the docs as the current truth.

WHAT IT GIVES UP
No joins, and queries must be planned before the schema.
Heavy compaction competes with reads for disk.
With no leader, conflicting writes are resolved by simple rules (such as last-writewins) instead of by transactions.
USE IT IN YOUR WORK

Model tables around queries, not entities. Pick the partition key so one query hits one partition, avoid unbounded partitions, and denormalise on purpose. The write path (log → memtable → SSTable) is why writes are cheap and reads are the expensive side.

SAY IT IN AN INTERVIEW

“Cassandra is Dynamo’s ring, gossip and replication on top of Bigtable’s commitlog, memtable and SSTable storage engine, built for Inbox Search. Writes are fast; you design the model around your queries.”

IF YOU REMEMBER ONE THING

Design the table for the query you will run, not for the data you have.
