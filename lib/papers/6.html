WHAT IT GIVES YOU The majority-quorum logic behind most replicated databases

THE PAPER IN ONE LINE

Agree on one value by asking a majority twice: first to find out whether a value may already be chosen, then to lock it in.

IN EVERYDAY TERMS

Five friends must pick one restaurant by phone, but any of them may lose signal at any time. Before proposing a place, you ask a majority, “has anyone already settled on something?” If yes, you must back that choice, not yours. That one rule is Paxos.

THE PROBLEM

Several machines must agree on one value: who is the leader, or which command is next in the log. Machines crash and restart, and messages arrive late, twice, or never. This is called consensus.

Lamport’s assumptions are friendly: nodes may crash and recover but do not lie, and messages may be lost or delayed but not corrupted.

THE BIG IDEA

Paxos has three roles. One physical server usually plays all three.

Proposer

Suggests a value. Several may compete.

Acceptor

Votes. It is the system’s memory: it remembers what it promised and accepted.

Learner

Finds out which value was chosen. A value is chosen once a majority

of acceptors accepted it.

The one insight to remember

Phase 1 exists to discover whether a value might already be chosen. If it might, the new proposer must adopt it instead of overwriting it. That single rule makes it impossible for two different values to be chosen.

HOW IT WORKS

The protocol in two phases

Single-decree Paxos with 3 acceptors. Any 2 of 3 form a majority, so one crashed acceptor does not stop progress.

Prepare A proposer picks a unique, increasing number n and asks a majority of acceptors: “promise to ignore anything numbered below n, and tell me what you already accepted.”

Promise Each acceptor promises (if n is its highest so far) and reports the highestnumbered proposal it already accepted, if any.
Accept If a majority promised, the proposer sends Accept(n, v) . The value v must be the one from the highest-numbered proposal reported. Only if there was none may it use its own.
Accepted An acceptor accepts unless it promised a higher number. When a majority accepts, the value is chosen.

Any two majorities overlap in at least one node. That overlapping node is the witness that carries knowledge from one round to the next.

From one value to a replicated log

Real systems need a sequence of decisions, not one. Multi-Paxos runs one Paxos instance per log slot. A stable leader skips Phase 1 for later slots, so the steady-state cost is one round trip: Accept, then Accepted.

KEY TERMS

Consensus

Several machines agreeing on one value despite failures.

QuorumA group big enough that any two such groups overlap. Usually a majority.
SafetyNothing bad ever happens, such as two different values chosen.
LivenessSomething good eventually happens, such as a value being chosen.
WHAT IT GIVES UP
Paxos always guarantees safety, but liveness only with luck: two proposers can keep outbidding each other forever. So you elect a distinguished proposer.
The paper leaves leader election, membership changes and many engineering details open. That is why implementations diverge, and why Raft (next chapter) was written.
USE IT IN YOUR WORK

Paxos-family protocols run underneath Chubby (Ch. 7), Spanner (Ch. 10) and DynamoDB’s per-partition replication (Ch. 11). The practical rule for your own designs: use 2f + 1 replicas to survive f failures, and wait for a majority, never for “all”.

SAY IT IN AN INTERVIEW

“Paxos chooses a value in two phases. Phase 1 blocks older proposals and discovers any value already accepted; Phase 2 proposes that value. Majority overlap guarantees two different values can never both be chosen.”

IF YOU REMEMBER ONE THING

Ask a majority twice, and always adopt a value that may already be chosen.
