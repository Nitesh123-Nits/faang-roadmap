THE PAPER IN ONE LINE

Store petabytes by sharding a sorted (row, column, time) map into tablets that live on GFS and are coordinated by Chubby.

IN EVERYDAY TERMS

A giant dictionary printed in order, torn into volumes. Each volume (tablet) sits on a different shelf, and a small index tells you which volume holds your word. New entries go in a notepad first and get merged into fresh printed volumes later.

THE PROBLEM

Google products such as web indexing, Earth and finance needed to store structured data at petabyte scale, from batch jobs to latency-sensitive serving. A file system (GFS) was too low-level, and a relational database could not spread across thousands of machines. Bigtable is the middle path.

THE BIG IDEA

The paper calls it a sparse, distributed, persistent, multi-dimensional sorted map. Plainly: look up by (row key, column, timestamp) and get bytes back.

HOW IT WORKS

Standing on other building blocks

GFS (Ch. 4)

Stores the commit log and the SSTable files. Bigtable does not do its own replication.

Chubby (Ch. 7)

Picks the single active master, tracks live tablet servers, and stores the root of the location hierarchy and schema.

SSTable

An immutable, sorted key→value file with a block index. Immutable means no locks on reads.

Tablet server

Serves reads and writes for a set of tablets. Clients talk to it directly.

Life of a write and a read

Writes are cheap sequential appends. Reads pay for it by merging a few places.

Write Append to the commit log in GFS, then insert into the in-memory memtable.
Flush When the memtable is full, write it out as a new SSTable (a “minor compaction”). Later, merge SSTables (“major compaction”) to keep reads fast.
Read Merge a view of the memtable and all relevant SSTables. The newest data wins.

How a client finds the right tablet

Chubby file Holds the location of the root tablet.
Root tablet Points to the METADATA tablets.
METADATA tablets Say which server holds each user tablet.
User tablet Your data, as SSTables in GFS.

Three hops, and clients cache locations aggressively. With an empty cache a lookup costs three round trips; with a stale cache, up to six. Most lookups never touch the hierarchy.

Performance refinements

Locality groups keep column families that are read together in the same files. Compression works very well because similar pages sit next to each other. Bloom filters avoid touching files that cannot contain a row, and several cache layers reduce disk reads.
